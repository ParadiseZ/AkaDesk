# AkaDesk 视频主链路设计

## 1. 文档目的

本文档用于定义 AkaDesk V1 的视频主链路设计，重点固定：

- `runtime/video` 到底负责什么
- 主控如何声明视频偏好
- 被控如何选择编码实现
- 主控如何优先硬解并回退到同编码软解
- 码率、分辨率、FPS 后续如何重配
- 视频链路异常时如何降级和恢复

本文档只定义视频主链路，不展开音频、输入、完整协议字段和具体代码实现。

## 2. 文档位置与代码落位

本文档固定放在：

- `docs/视频主链路设计.md`

后续代码落位：

- 视频编排：`desktop/host/runtime/src/video/`
- 采集抽象：`desktop/host/contracts/src/cap/`
- 编码抽象：`desktop/host/contracts/src/encode/`
- Windows 实现：`desktop/host/windows/src/cap/`、`desktop/host/windows/src/encode/`
- Linux 实现：`desktop/host/linux/src/cap/`、`desktop/host/linux/src/encode/`

## 3. V1 最终口径

V1 当前固定遵守下面这条：

1. 主控端在会话协商阶段下发目标视频编码信息。
2. 被控端按协商结果输出该编码的视频流。
3. 主控端优先使用该编码的硬解。
4. 如果主控端不支持该编码硬解，则回退到同编码软解。
5. V1 先只正式落 `H.264`。
6. `HEVC`、`VP8`、`VP9`、`AV1` 只预留扩展位，不并行落地。

补充：

- Host 端也优先使用可用的硬编。
- 如果 Host 端没有可用硬编，则回退到同编码软编。
- 主控解码回退和 Host 编码回退是两件不同的事，分别处理。

## 4. 主链路边界

## 4.1 `runtime/video` 负责

- 消费 `VideoPreference`
- 生成最终 `VideoSessionSpec`
- 决定 Host 端优先硬编还是软编
- 组织采集帧进入编码器
- 管理编码器生命周期
- 将编码后视频包送入 WebRTC 发送通道
- 接收运行时统计并判断是否需要降级或重配

## 4.2 `runtime/video` 不负责

- 直接调用平台采集 API
- 直接调用平台编码 API
- 直接实现主控端解码器
- 决定 UI 怎么展示
- 解析 Proto 消息

## 4.3 相关模块职责

- `cap`
  - 输出原始视频帧
- `encode`
  - 提供编码实现能力和编码会话
- `runtime/video`
  - 编排采集、编码、发送和重配
- `WebRTC`
  - 负责真正网络发送
- `Android Controller`
  - 负责最终解码选择和播放

## 5. 主链路输入与输出

## 5.1 输入

视频主链路至少接收这些输入：

- `VideoPreference`
- `DisplayId`
- `CaptureTargetId`
- 当前平台 `CaptureCapabilitySnapshot`
- 当前平台 `VideoEncoderCapabilitySnapshot`

`VideoPreference` 当前最重要字段：

- `codec`
- `width`
- `height`
- `fps`
- `bitrate_kbps`
- `allow_same_codec_software_fallback`

## 5.2 输出

视频主链路至少输出这些结果：

- `VideoSessionSpec`
- `EncoderSelection`
- `VideoPipelineState`
- 编码后视频包流
- 诊断事件和降级事件

## 6. 核心状态与对象

建议 `runtime/video` 至少有这些内部对象：

- `VideoPreference`
- `VideoSessionSpec`
- `EncoderSelection`
- `VideoPipelineState`
- `CaptureSessionHandle`
- `VideoEncoderHandle`
- `VideoStreamStats`

建议语义：

- `EncoderSelection`
  - 记录当前使用 `hardware` 还是 `software`
- `VideoPipelineState`
  - 记录 `idle/preparing/running/degraded/stopping/error`
- `VideoStreamStats`
  - 记录发送帧率、编码耗时、码率、关键错误计数

## 7. 会话建立阶段的视频流程

## 7.1 流程概览

```text
VideoPreference
  -> Runtime 判断支持范围
  -> 选择 Host 端编码实现
  -> 准备采集
  -> 准备编码器
  -> 生成 VideoSessionSpec
  -> 交给 WebRTC 建立发送轨
  -> 进入 Streaming
```

## 7.2 详细步骤

1. 主控端提交 `VideoPreference`
2. Runtime 校验是否为当前支持 codec
3. V1 中只接受 `H.264`
4. Runtime 查询平台可用编码实现
5. Runtime 优先尝试 `H.264` 硬编
6. 若 Host 无可用 `H.264` 硬编，则尝试 `H.264` 软编
7. Runtime 准备采集目标
8. Runtime 准备编码器
9. Runtime 生成最终 `VideoSessionSpec`
10. Runtime 将 `VideoSessionSpec` 回传到协商结果
11. WebRTC 发送轨建立完成
12. 视频链路进入 `STREAMING`

## 8. Host 端编码选择策略

## 8.1 V1 默认顺序

V1 对 `H.264` 的 Host 端选择顺序建议固定为：

1. `H.264 hardware encoder`
2. `H.264 software encoder`
3. 都不可用则会话建立失败

## 8.2 选择依据

Runtime 在选择时至少要看：

- codec 是否支持
- 分辨率是否支持
- FPS 是否支持
- 目标码率是否在能力范围内
- 当前实现是否可初始化

## 8.3 失败处理

- 硬编能力声明可用，但初始化失败
  - 若允许软编回退，则回退到同编码软编
  - 否则进入会话失败

- 软编也初始化失败
  - 当前会话进入 `FAILED`

## 9. 主控端解码选择与回退

## 9.1 当前规则

主控端对最终协商 codec 的解码选择顺序固定为：

1. 同编码硬解
2. 同编码软解
3. 都不可用则当前会话失败

V1 中这个“同编码”就是：

- `H.264`

## 9.2 解码回退触发点

建议把主控端解码回退触发点分成三类：

1. 会话建立前就知道该硬解不可用
2. 解码器初始化失败
3. 解码运行中出现不可恢复错误

## 9.3 主控端上报语义

主控端至少需要把下面这些信息反馈回控制层或诊断层：

- 当前实际解码实现：`hardware` / `software`
- 是否发生回退
- 回退原因

这不是为了让 Host 改 codec，而是为了：

- 更新会话诊断
- 让 Runtime 进入 `DEGRADED`
- 让 UI 能展示“当前处于软解回退”

## 10. `DEGRADED` 的进入与恢复

## 10.1 进入条件

视频主链路进入可恢复降级的典型条件：

- 主控端从 `H.264` 硬解回退到 `H.264` 软解
- Host 端从 `H.264` 硬编回退到 `H.264` 软编
- 码率被迫下调
- FPS 被迫下调

## 10.2 状态影响

建议语义：

- `SessionState` 仍可保持 `STREAMING`
- `RuntimeState` 进入 `DEGRADED`
- `VideoPipelineState` 标记 `degraded`

## 10.3 恢复条件

只有在下面条件满足时才允许从 `DEGRADED` 回到正常：

- 当前编码器/解码器恢复到稳定工作态
- 最近错误计数回落
- 当前配置已稳定运行一段窗口时间

## 11. 码率、分辨率、FPS 重配

## 11.1 哪些可以动态改

V1 建议允许后续动态调整：

- `bitrate_kbps`
- `fps`

V1 暂不优先做无缝动态切换：

- 分辨率
- codec

分辨率在 V1 可以支持，但建议按“重配或重建链路”处理，而不是追求完全无缝。

## 11.2 触发来源

可能的重配触发来源：

- 主控端主动修改偏好
- Runtime 根据网络/性能做保守下调
- 平台能力变化导致被动调整

## 11.3 重配顺序

建议顺序：

1. 更新目标参数
2. 判断当前编码器是否支持就地重配
3. 若支持，则直接 `reconfigure_video_encoder`
4. 若不支持，则停止当前编码器并重建
5. 更新 `VideoSessionSpec`
6. 推送新的会话快照与诊断信息

## 11.4 不建议的 V1 行为

V1 不建议：

- Streaming 中途切换 codec
- Streaming 中途在多 codec 间自动来回探测

原因：

- 会极大增加链路复杂度
- 对当前 V1 目标收益不高

## 12. 采集与编码的协作

## 12.1 采集输出

`cap` 层输出：

- 原始帧
- 帧时间戳
- 源分辨率信息

## 12.2 编码输入

`encode` 层接收：

- 原始帧
- 当前编码目标参数
- 当前会话相关上下文

## 12.3 关键原则

- `cap` 不直接知道 WebRTC
- `encode` 不直接控制采集设备
- `runtime/video` 才是两者的编排者

## 13. 异常处理规则

## 13.1 直接失败

以下情况直接判为当前会话失败：

- `VideoPreference.codec` 非当前支持 codec
- 无可用 `H.264` 硬编，且无可用 `H.264` 软编
- 采集目标不可用且无替代路径
- WebRTC 视频发送轨无法建立

## 13.2 可恢复异常

以下情况优先走降级：

- 硬编初始化失败但软编可用
- 硬解初始化失败但软解可用
- 当前配置过高导致帧率不稳，可以降低 `bitrate/fps`

## 13.3 必须记录的诊断信息

至少记录：

- 协商 codec
- Host 实际编码实现
- 主控实际解码实现
- 是否发生回退
- 回退原因
- 最近一次重配原因
- 当前分辨率/FPS/码率

## 14. V1 最小实现范围

如果只按最小闭环落地，视频主链路第一版必须包含：

1. `H.264` 单 codec 协商
2. Host 端 `H.264` 硬编优先
3. Host 端 `H.264` 软编回退
4. 主控端 `H.264` 硬解优先
5. 主控端 `H.264` 软解回退
6. `runtime/video` 基本状态和诊断事件
7. `bitrate/fps` 基本重配能力

第一版可以暂时不追求：

- `HEVC`
- `VP8`
- `VP9`
- `AV1`
- Streaming 中途 codec 切换
- 极复杂的自适应码控

## 15. 本次结论

视频主链路设计文档固定放在：

- `docs/视频主链路设计.md`

它定的是：

- `runtime/video` 如何组织采集、编码、发送
- Host 端如何选硬编/软编
- 主控端如何选硬解/软解并回退
- 什么时候进入 `DEGRADED`
- V1 允许哪些动态重配

后续如果继续，最自然的动作就是把这里的 `VideoPipelineState`、`EncoderSelection` 和 `runtime/video` 生命周期收敛成真正的 Rust 领域模型和服务接口。
