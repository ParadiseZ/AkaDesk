# 15-M4 收口审计与执行记录

## 1. 目标

以“Android 主控端能按正常远控流程操作，并最终持续远控且看到被控页面画面”为最终收口目标，按真实实现现状把 `M4` 未完成项拆成可执行小任务，并持续记录已完成内容。

## 2. 当前审计结论

### 2.1 已经落地但需要继续利用的持久化基础

- Host 身份已落盘：
  - `desktop/host/runtime/src/pairing/mod.rs`
  - `host_identity.json`
- Host 配对凭证已落盘：
  - `desktop/host/runtime/src/pairing/mod.rs`
  - `pairings.json`

- Host 远控设置已落盘：
  - `desktop/host/runtime/src/settings.rs`
  - `host_settings.json`
  - 已包含：
    - `temporary_verification_code`
    - `custom_verification_code`
    - `verification_mode`
    - `connection_method`
    - `refresh_temporary_code_after_controlled_end`
- Android 主控本地已保存：
  - `controller_device_id`
  - 每台被控设备的 `pair_token`
  - `历史 / 收藏 / 已配对`
  - 视频编码偏好

### 2.2 当前真正卡住 `M4` 收口的缺口

#### A. 持久化设置已经开始驱动真实认证，但还缺联调证据

当前已不再是“设置只保存、不生效”的状态：

- `temporary_verification_code`
- `custom_verification_code`
- `verification_mode`
- `connection_method`
- `allow_remote_assistance`

都已经开始参与 Host 控制层的真实认证与门禁流程。

当前这部分的真实剩余问题，不再是“没接上逻辑”，而是：

- 还没有真实 Windows + Android 联调证据证明这组持久化设置在普通远控流程下长期稳定
- `TRUST_ONLY` / `ACCESS_CODE_AND_CONSENT` 仍缺更细粒度的错误码、提示文案和边界收口

#### B. consent 主线已有第一版真实闭环，但还没有验收到“稳定可用”

当前已不再是“只有设置和文档，没有真实 consent 链”的状态：

- Host 已有真实 `pending remote request`
- 桌面壳已能看到真实来电请求
- 被控端本地同意/拒绝已能回到 Host Runtime
- `TRUST_ONLY`
- `ACCESS_CODE_AND_CONSENT`

都已经有第一版真实控制层闭环。

当前这部分的真实剩余问题，是：

- 还没有联调证明普通远控流程下这条 consent 链稳定命中
- 还没有补多请求排队、来源设备展示和失败收口细节

#### C. 当前最大的真实阻塞已经收敛到 `T4.2 + T5.1`

现在真正卡住 `M4` 最终收口的，已经不是验证码或连接方式持久化本身，而是：

- Host `H.264 -> WebRTC` 真实发送链是否稳定把媒体送到 Android
- Android `Offer/Answer/ICE -> VideoTrack -> 首帧 -> 持续收帧` 是否稳定出画面

也就是说，当前最核心的问题已经收敛成：

- Host 是否稳定发出第一张可解码关键帧
- Android 是否稳定接住第一张关键帧并真正显示
- 之后的视频帧是否能持续流动，而不是只停在协商成功或一帧起播

### 2.3 当前最小收口主线

为了避免继续把工作做复杂，后续主线只保留三段：

1. 保持 `T1/T2` 当前真实闭环不回退
2. 把 `T3` 第一版 consent 链补到“可联调验证”
3. 只围绕 `T4.2 + T5.1` 收真实出画面链：
   - Host 稳定发第一张可解码关键帧
   - Android 稳定收到首帧并显示
   - 然后把持续视频流跑稳

- `TRUST_ONLY` 已不再直接报“未实装”，而是进入真实本地确认等待链路
- `ACCESS_CODE_AND_CONSENT` 已改为“先验证码、后本地确认”的两段式链路
- Android 主控已识别 `LOCAL_CONFIRM` 挑战，改走等待弹层，而不是继续错误弹验证码表单
- Android 主控在收到 `AUTH_ACCESS_CODE_AND_CONSENT_REQUIRED` 时，当前也会先回到“输入验证码”入口：
  - 不再先盲发 `PairingRequest`，等 Host 回 `PairingChallenge` 后才把用户拉回验证码表单
  - 这样“先验证码、再本地同意”的正常远控顺序，在 Android 侧入口上终于和文档语义一致
- Android 主控在收到 `StartSessionAccepted` 后，当前也会显式清掉上一段的认证/同意临时状态：
  - 包括动作菜单、验证码弹层、等待允许弹层，以及自动起会话的挂起标记
  - 这样“认证/同意”阶段和“会话建立”阶段的 UI/状态边界不再混在一起，减少 accepted 后仍残留旧入口状态的干扰
- Android `AndroidWebRtcSession` 在重新绑定 `SurfaceViewRenderer` 时，当前也会先释放旧 renderer 生命周期，再重新 `init(...)`：
  - 不再让同一个 renderer 带着上一条 WebRTC 会话留下的初始化状态，直接被新会话再次绑定
  - 这样可以减少“会话已 accepted 且新 WebRTC 会话已创建，但首帧仍挂不上真实渲染器”的跨会话渲染器复用问题
- Android 主控在收到“不同 `sessionId` 的新 `SessionChangedEvent`”时，当前也会先关闭旧 `AndroidWebRtcSession`：
  - 不再只清 Host 出包/transport 状态，而把上一条会话的 WebRTC/首帧状态继续留在界面上
  - 这样可以减少旧会话最后一帧残留、把新会话误显示成“已经有画面”的跨会话串台
- Android 主控现在也开始对远端视频轨 / 首帧 / 卡流 / 恢复 / WebRTC 失败回调按 `sessionId` 做显式门禁：
  - 旧会话迟到的 WebRTC 回调，不再继续改当前活动会话的 `activeRemoteVideoReady`、`activeRemoteVideoStalled` 或当前摘要
  - 这样可以减少“上一条会话迟到回调把新会话误判成已首帧 / 已停滞 / 已失败”的跨会话状态污染
- Android `SurfaceViewRenderer` 在切会话、解绑或重新绑定时，当前也会显式 `clearImage()`：
  - 不再只移除 sink 或 release renderer，而让旧会话最后一帧继续残留在屏上
  - 这样可以减少“新会话其实还没首帧，但界面还停着上一条会话旧画面”的假持续出画面
- Android 主控在收到 `StartSessionAccepted` 后，当前也会立刻创建对应的 `AndroidWebRtcSession`：
  - 不再等 `WebRtcOffer/ICE` 到了才按需临时创建本地 answerer
  - 这样 `PeerConnection`、`recvonly` 视频 transceiver 和 renderer 绑定会更早就位，减少 Host accepted 后紧接着 flush signaling 时 Android 侧准备仍偏晚的风险
- Android `AndroidWebRtcSession` 现在也开始把远端 ICE candidate 队列与去重集合收成带锁访问：
  - `addRemoteIceCandidate()`、`drainPendingRemoteCandidates()`、`applyRemoteIceCandidate()` 和关闭清理路径不再并发裸读写同一组 pending/applied candidate 容器
  - 这样可以减少 `Offer` 生效、`Answer` 生成和远端 ICE 迟到交错时的 candidate 丢失、重复或回退重试链路被破坏，直接服务于首帧建立
- Host transport 现在也不再把 `PeerConnectionState::Disconnected` 直接当成硬失败：
  - 临时 `Disconnected` 当前只会记录到 Host 视频/transport 状态里，给 WebRTC 链路保留恢复机会
  - 只有 `Failed` / `Closed` 才会继续把会话直接打到失败
  - 这样可以减少持续远控过程中可恢复网络抖动被立即打成整条会话断开的情况，更贴近“持续出画面”目标
- Host transport 对临时 `Disconnected` 的错误传播现在也开始收口到 transport 域本身：
  - 不再把“WebRTC 链路暂时断开”继续写进 `HostVideoStreamEvent.latest_error`，误污染成 Host 编码/出包异常
  - transport 状态在重新回到 `Connected` 时也会主动清掉自身残留的临时错误
  - 这样可以减少“网络抖动”被误判成“Host 出包链已坏掉”，更准确地区分持续视频流里的媒体问题和传输问题
- Android 主控在控制 WebSocket 失败时，当前也不再无条件关闭现有 WebRTC 画面链：
  - 只要当前会话 `sessionId` 已明确且本地 `AndroidWebRtcSession` 已创建，当前就会先保留现有 WebRTC 媒体链
  - 不再立刻 `closeWebRtcSession()` 把现有被控画面主动掐掉
  - 这样不仅能减少“已有画面时被自己主动断掉”，也能减少“会话已 accepted、首帧还在路上时就被控制信道抖动提前掐掉”的首帧中断
  - 同时，这条分支也不再把对应 Host 本地状态打成 `Failed`
  - 避免出现“现有被控画面仍在继续，但设备状态已经显示失败”的自相矛盾语义
- Android 主控在“保留现有媒体链”分支下，当前也会按 `1s -> 2s -> 4s -> 8s` 退避自动重连控制通道：
  - 不再只是把 `controlSession` 置空，然后把当前媒体链完全留给用户手动补救
  - 这条重连路径会显式复用当前活动会话和现有 `AndroidWebRtcSession`，不再走会先 `closeWebRtcSession()` 的普通 `connect(...)`
  - `HostControlSession.close()` 也开始显式静默关闭，避免主动轮换 control session 时被旧 listener 反向上报成真实连接失败
  - 如果这条恢复链最终落到 `PairingRequired`，当前也不再把用户半路拉回验证码/等待允许流程，而是直接认定当前远控会话恢复失败并结束本地会话
  - 如果控制通道恢复认证成功，但在短超时窗口内始终没有任何活动会话恢复信号（`SessionChangedEvent` / `WebRtcOffer` / Host 视频状态 / transport 状态），当前也会主动结束这条旧会话
  - 避免 Android 在 Host 端其实已经没有可恢复活动会话时，继续无限保留旧画面链和旧会话态
- Android `HostControlSession` 当前也开始跑最小 `HeartbeatPing/Pong` 闭环：
  - Host 既有的 `HeartbeatPing -> HeartbeatPong` 响应能力，现在终于被 Android 控制通道实际消费起来
  - Android 会周期性发 `HeartbeatPing`，并在连续超时后把当前 control channel 视作失活，接到现有“保留媒体链并自动重连 control session”的恢复路径
  - 这样控制通道不再只能被动等底层 WebSocket 明确失败，持续远控时能更早发现“媒体仍在，但控制层已经失活”的情况
- Host 控制层在 `ControlHello` 认证成功后，当前也会尝试把“当前活动会话”重新绑定到这条新 control connection：
  - 如果当前活动会话的 `controller_device_id` 和这次重新认证成功的 Android 控制端一致，就会立刻恢复这条连接自己的 `active_session_id`
  - 这样已有的 `SessionChangedEvent` / Host 视频状态 / transport 状态 pump 会继续在新连接上恢复工作，而不是只恢复了控制 WebSocket 本身，却丢掉了会话状态和媒体状态推送
- Host `ControlHello` 对 `pair_token` 的接受条件，当前也开始为“已有活动会话重绑”开最小例外：
  - 即使当前 `connection_method` 不是 `ACCESS_CODE`，只要这次重连的 Android 控制端本身就是当前活动会话的 owner，且 `pair_token` 校验通过，就允许这条新 control connection 重新接回当前活动会话
  - 这样现有自动 control reconnect 才不会在 `TRUST_ONLY / ACCESS_CODE_AND_CONSENT` 的活动会话里天然失败，同时又不会把新的日常远控入口整体放宽
- Android 主控当前也开始缓存本地 `WebRtcAnswer` 和本地 ICE candidate，并在控制通道重连认证成功后补发：
  - 不再是“本地 signaling 生成即直发”，控制通道一断就直接蒸发
  - 这样如果 `AndroidWebRtcSession` 已经生成了本地 `Answer/ICE`，但 control channel 恰好在这段窗口里断开，现有重连链恢复后也能把这批本地 signaling 补送回 Host
- Host 本地 `WebRtcOffer` / 本地 ICE 当前也开始区分“待发送”和“已发送但可重放”：
  - 正常发送成功后，不再是简单从 signaling 状态里彻底抹掉，而是保留最近一次已发出的 `Offer/ICE` 作为可重放副本
  - 当 control reconnect 把当前活动会话重新绑回新连接时，这批已发出的本地 signaling 会重新挂回待发送队列，再次送给 Android
  - 这样可以减少“Host 这边已经成功写到旧控制连接，但 Android 实际没收到；重连后 Host 端却没有任何东西可重发”的首帧阻塞
- Android 主控当前也开始按真实控制协议请求结束远控会话：
  - 断开按钮不再一上来就只做本地 `closeWebRtcSession()` 和 `controlSession.close()`
  - 当前会先通过 control channel 发送 `StopSessionRequest(session_id)`，把本地状态切到 `DISCONNECTING`，再等待 Host 回推终止事件后统一收尾
  - 如果用户点断开时 control channel 正好已经断开，这条请求也不再直接丢掉，而是会挂进现有 control reconnect 链，待控制通道恢复后优先补发
  - 如果 `StopSessionRequest` 发出后长时间没有任何关闭确认，当前也会优先强制重连 control channel 再补发，而不是一直卡在 `DISCONNECTING`
- Host 控制层当前也开始处理 `StopSessionRequest`：
  - 仅允许当前已认证 controller 结束自己持有的活动会话
  - 收到后会把会话标成 `DISCONNECTED`，结束视频/transport/signaling 运行态，并回推 `SessionClosedEvent(reason = CONTROLLER_REQUEST)`
  - 这样“正常断开”终于开始从本地直接掐断，收成真实协议链的一部分
- Host transport 对远端 ICE candidate 现在也不再是一条失败就永久丢弃：
  - 新到的远端 candidate 如果 `add_ice_candidate` 失败，当前会先进入有限次重试队列，而不是立即永不重试
  - 延迟重试仍失败到上限后，才作为 transport 错误保留
  - 这样可以减少 `Answer/ICE` 时序交错或链路尚未完全 ready 时，远端 candidate 一次失败就永久丢失，进而影响首帧建立或后续持续流恢复
- Host transport 在远端 ICE candidate 重试成功后，当前也会主动清掉 transport 残留错误：
  - 不再让“candidate 已补写成功”的链路继续挂着旧的 transport error
  - 这样可以减少恢复后的 transport 仍被 Android 误判成持续异常
- Android `AndroidWebRtcSession` 现在也不再只在“本地 Answer 尚未生效”时才回退远端 ICE candidate：
  - 远端 candidate 如果 `addIceCandidate()` 失败，当前会进入有限次延迟重试，而不是在本地 Answer 发出后直接一次失败就丢
  - 这样可以减少 Android 侧 `Offer/ICE` 时序交错时，远端 candidate 一次未被接收就永久丢失，进而影响首帧建立或后续恢复
- 桌面壳已改为从 Host Runtime 的真实 pending request 读取来电请求，不再只依赖本地 preview 假数据
- Android 主控的“等待对方允许”入口已改成真实发起连接，而不是只弹等待 UI
- Host 视频准备阶段已改成优先截取真实主屏一帧 BGRA 送入现有 H.264 编码链；若真实截帧或编码失败，再回退到原合成测试图
- Host Runtime 已新增最小后台视频循环：
  - `StartSessionRequest` 建立会话后会启动连续采集 + 连续编码线程
  - 首帧成功编码后，会把会话状态从 `PREPARING` 推进到 `STREAMING`
  - 后续在当前活动会话存续期间持续刷新会话时间戳，直到会话被替换或结束
- Host Windows `ffmpeg` 侧已把连续视频循环改为复用同一个 H.264 编码会话：
  - 会话启动时一次性选定 encoder、分配 BGRA/YUV 帧缓冲和 `sws` 上下文
  - 后续连续帧复用同一套编码上下文递增 `pts`
  - 不再在视频循环里每帧重新打开 encoder
- Host Runtime 已新增共享视频流状态，开始承接真实编码包输出：

    - 一旦已经开始真实远控，后续短暂抓屏失败或单帧编码失败会先按最小重试预算继续尝试，而不是立刻把视频切成 synthetic 画面
    - 运行中的这类短暂错误还会顺带触发“下一次恢复成功时强制打一张关键帧”
    - 连续错误超过预算后才会把会话打到失败
    - 目的是优先保持“持续看到被控页面”这条目标，不再让运行中的真实桌面流被 synthetic 占位画面替换，并减少恢复后继续等待自然关键帧的时间
  - Host signaling 状态现在也开始把远端 `Answer` 处理成幂等：
    - 同一活动会话的第一份 `Answer` 会被锁定
    - 后续重复 `Answer` 或不同 SDP 的后续 `Answer`，当前都不会再覆盖这份已存 `Answer`
    - 目的是减少控制信道抖动时，远端 `Answer` 被重复或乱序覆盖带来的时序漂移
  - Host 控制层现在只会在“首份远端 `Answer` 真正入库”时推进后续链路：
    - 重复 `Answer` 不再继续触发后续 signaling flush
    - 不同 SDP 的后续 `Answer` 也只会显式忽略，不再继续按“stored”口径往下走
    - 目的是减少重复/乱序 `Answer` 把 Host 后续 signaling 时序再次扰动
  - Host 控制层现在也只会在“新的远端 ICE candidate 真正入库”时推进后续链路：
    - 重复远端 candidate 不再继续触发后续 signaling flush
    - 目的是减少重复 candidate 在 Host 控制层继续搅动后续 signaling 时序
  - Android 主控现在在本地 WebRTC 会话发生硬失败时，会先回收当前 `AndroidWebRtcSession`：
    - 不再只改摘要而保留一条已坏掉的本地 `PeerConnection`
    - 这样后续同会话再次收到 `Offer/ICE` 时，可以从干净的本地 WebRTC 会话重新拉起
- Android 已开始接入真实 WebRTC answerer 骨架：
  - `android/app` 已接入 `org.webrtc:google-webrtc`
  - 新增 `AndroidWebRtcSession`，收到 `WebRtcOffer` 后会真正创建 `PeerConnection`
  - Android answer 侧现在会在 `setRemoteDescription` 之前预置一个 `RECV_ONLY` 视频 transceiver，主动声明“本端就是要接视频”，减少只靠远端 Offer 被动拉起视频 m-line 的协商歧义
  - Android 侧会把远端 `Offer` / `ICE candidate` 写进本地会话，并在生成本地 `Answer` / 本地 ICE 后经控制信道回传给 Host

      - 不再只依赖 Compose 后续一次 `AndroidView.update(...)` 恰好再触发，才把 renderer 重新绑到晚创建的 WebRTC 会话
      - 目的是减少“UI 画面容器已经挂起，但本地 WebRTC 会话稍后才创建，导致首批远端视频轨没有及时挂到真实 renderer”这类时序性掉链

      - 如果远端视频轨已经存在，即使 `onTrack/onAddTrack` 回调还没来或没有按预期先触发，也会主动把这条 `VideoTrack` 挂到观察器和 renderer
      - 目的是减少“远端视频轨其实已经在 PeerConnection 里了，但当前实现只靠回调发现，导致首批视频帧没有及时接到观察器”这类时序性掉链

      - 即使远端视频轨是在连接建立途中或 renderer 绑定之前就已经准备好，也会在这些关键节点再次尝试挂接
      - 目的是进一步减少“轨道已存在但发现时机漂掉，首批视频帧没有及时进观察器或 renderer”这类时序性掉链
    - 如果回调或主动扫描再次命中的是“同一条远端 `VideoTrack`”，当前也会重新补挂观察器和 renderer sink：
      - 不再在“同轨重发现”时直接 early return
      - 目的是减少首帧或恢复阶段因 sink 状态漂移导致的同轨漏绑
    - Android answer 侧现在在“远端 ICE candidate 成功写入本地 `PeerConnection`”后，也会立刻补扫一次现有远端视频轨：

      - 目的是进一步减少“ICE 已接上，但远端视频轨已存在 yet 尚未及时挂到观察器/renderer”的首帧时序空窗
    - 一旦后续 Host 侧真的推来 WebRTC 视频轨，Android 页面不需要再回头重搭渲染容器

  - Android 侧现在已有最小卡流观测：首帧后若 2.5s 内没有继续收到新帧，会把会话摘要标成“远端视频流疑似停滞”；后续有新帧恢复时，也会把状态切回“远端视频流已恢复”
  - Android 远控页现在也会在保留最后一帧画面的同时叠加“视频流疑似停滞”告警，不再只能靠底部摘要文字判断流是否已经卡住

  - Android 远控页现在还能同时看到 Host transport 发送状态；如果 `peer_connection_state` 已异常、`remoteAnswerApplied=true` 但 sample 计数仍不增长、或者 transport 自身上报错误，会叠加 `Transport 发送异常` 告警，并在底部显示 transport 摘要
  - Android 主控现在还会把 `Android 收帧状态 + Host 出包状态 + Host transport 状态` 汇总成一条派生视频链路诊断：

    - 能区分“Host 出包已停滞”
    - 能区分“Transport 已异常”
    - 能区分“Host 还在发，但 Android 接收或渲染链疑似停滞”

  - Android 主控收到 `FAILED` / `DISCONNECTED` 的 `SessionChangedEvent` 后，现在会主动收掉本地 WebRTC 会话、清理当前远控态并给出断开提示，而不再继续停在假性的“等待媒体/正在远控”

### 4.5 后续继续时的顺序

1. 保持当前 `T1/T2` 的验证码 / 连接方式持久化闭环不回退
2. 在当前第一版 `T3` 基础上补真实联调收口，而不是再回去重写门禁主线
3. 把主要精力集中在 `T4.2 + T5.1`：
   - Host 稳定发第一张可解码关键帧
   - Android 稳定接到首帧并真正显示
   - 持续视频流稳定跑起来
4. 首帧和持续视频流稳定后，再回头补 `T5.2 / T5.3` 的长期体验与渲染细节
