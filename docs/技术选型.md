# AkaDesk 技术选型

## 1. 文档目的

本文档用于作为 AkaDesk 远程控制项目重启后的技术基线，先把 V1 的平台范围、核心栈、模块边界和暂不采用的方案固定下来，避免后续边做边改。

当前结论以仓库现状为基础：

- `android/` 已经是可构建的 Android 原生工程。
- `desktop/` 目录当前还没有形成可运行桌面端实现。
- 本次重启后，桌面端明确采用 `Tauri 2`，不再以 Compose Desktop 作为默认方向。

## 2. V1 产品范围

V1 只做最核心闭环：

- Android 作为主控端
- Windows 作为被控端
- 局域网发现与直连
- 基础画面传输
- 基础音频传输
- 基础输入控制
- 基础文件传输

V1 不优先投入：

- iOS / Linux 客户端
- 自建 NAT 穿透基础设施
- 复杂云中继
- 重型后台管理系统

## 3. 选型总览

| 领域 | 选型 | 结论 |
| --- | --- | --- |
| Android 主控端 | Kotlin + Jetpack Compose + Material 3 | 继续沿用，和当前仓库一致 |
| 桌面端 UI | Tauri 2 + TypeScript + Vue 3 | 作为 Windows 桌面壳和运维入口 |
| Windows 被控核心 | Rust | 负责采集、编码、输入注入、文件传输和会话管理 |
| 共享协议 | Protocol Buffers + 明确版本字段 | 代替“桌面/移动共用 Kotlin 模块”作为跨语言共享层 |
| 控制平面 | HTTP/WebSocket + 局域网发现 | 用于发现、配对、状态同步、文件元数据控制 |
| 数据平面 | WebRTC | 用于低延迟视频、音频、DataChannel 输入事件 |
| Android 本地存储 | DataStore | 保存连接历史、偏好设置、输入配置 |
| 桌面状态存储 | Tauri Store 或 SQLite | 只保存本地配置、最近设备、诊断信息 |
| Windows 原生能力 | Rust crate + 必要的 Windows API 封装 | 高频能力不放在 WebView 层 |
| 构建基线 | Android: AGP 9.2.1 + Gradle 9.5.1 + Kotlin 2.3.21 | 已在当前仓库验证可构建 |

## 4. 为什么这样选

### 4.1 Android 继续原生

Android 主控端对触控、手柄、键鼠映射、前后台切换、音视频播放、权限模型都比较敏感。原生 Kotlin + Compose 的收益很明确：

- 输入和媒体能力接入成本最低
- Compose 更适合快速迭代遥控器、设备列表、悬浮控件等 UI
- 与当前仓库已存在的 `android/` 工程连续，不需要推倒重来

### 4.2 桌面端 Tauri 2

桌面端不是高频媒体渲染核心，而是宿主壳、配置入口、诊断入口和安装分发入口，因此 Tauri 2 更合适：

- 包体小，资源占用比 Electron 更稳
- Rust 后端更容易和 Windows 被控核心共用部分底层能力
- 前端 UI 迭代效率高，适合做设备管理、设置页、日志页、诊断页
- 如果后续需要托盘、开机自启、权限引导、文件选择、窗口管理，Tauri 2 都更顺手

桌面端这里不承担高频采集/编码主循环。真正的高频能力仍然下沉到 Rust Host Core，Tauri 只负责壳层和控制入口。

### 4.3 不再把“共享 Kotlin 模块”作为主策略

如果桌面端也是 Kotlin/Compose Desktop，那么共享 Kotlin 模块是自然选择；但桌面端现在定为 Tauri 2 后，桌面 UI 侧已经变成 `TypeScript + Rust` 组合。

因此共享层需要改成“协议共享”而不是“语言共享”：

- 用 `proto/` 维护跨端协议
- Kotlin、Rust、TypeScript 分别生成或映射各自模型
- 协议里强制保留 `version`、`capabilities`、`codec`、`feature flags`

这样更适合 Android + Tauri + Rust Host 的多语言组合，也更利于后续独立升级。

## 5. 分层设计建议

### 5.1 Android 主控端

建议职责：

- 设备发现
- 配对与连接
- 视频/音频播放
- 触控/按键/手柄输入
- 文件上传下载入口
- 输入方案配置和偏好设置

建议技术：

- `Kotlin`
- `Jetpack Compose`
- `Material 3`
- `Navigation Compose`
- `DataStore`
- WebRTC Android SDK

不建议现在就引入很重的架构层或过度 DI。V1 优先把连接、画面、输入闭环跑通。

### 5.2 Tauri 2 桌面端

建议职责：

- Windows 宿主 UI
- 本地服务状态展示
- 局域网可见性和配对入口
- 编码/采集能力诊断
- 日志查看、导出和故障引导
- 文件传输记录和基础设置

建议技术：

- `Tauri 2`
- `Rust`
- `Vue 3`
- `TypeScript`
- `Vite`

选择 Vue 3 的原因很简单：做设置面板、设备列表、诊断页这类中后台式界面足够快，也方便和 Tauri 命令边界保持清晰。

### 5.3 Windows Host Core

建议职责：

- 屏幕采集
- 系统音频采集
- H.264 / VP8 视频编码策略
- Opus 音频编码
- 输入注入
- 文件收发
- 会话保活、断线重连、能力协商

建议技术：

- `Rust`
- Windows 原生 API 封装
- WebRTC 传输栈
- 必要时引入独立原生库处理高频编解码

这里要坚持一个原则：高频循环、时序敏感逻辑、媒体链路不要塞进 Tauri 前端。

### 5.4 协议与会话层

建议拆成两层：

- 控制平面：设备发现、握手、配对、心跳、状态同步、文件元数据
- 数据平面：视频、音频、输入事件、文件流

建议：

- 局域网发现使用 `mDNS` 或受控 UDP 广播
- 控制平面优先走 `WebSocket`
- 数据平面优先走 `WebRTC`
- 文件传输小文件可复用控制连接，大文件走独立流

这样做的好处是 UI 改动、设置页改动、发现逻辑改动，不会轻易影响到媒体链路。

## 6. 推荐目录结构

```text
docs/
  技术选型.md
  架构设计.md
  协议设计.md

android/
  app/

desktop/
  src-tauri/
  ui/

host/
  windows-core/

proto/
  session.proto
  device.proto
  transfer.proto
```

说明：

- `desktop/` 放 Tauri 2 桌面壳
- `host/` 放真正的 Windows 被控核心
- `proto/` 放跨端协议定义
- Android 不直接复用 Tauri 或 Rust UI 层，只复用协议

## 7. 当前仓库对应关系

当前已经落地的只有 Android 基线：

- `android/settings.gradle.kts`
- `android/build.gradle.kts`
- `android/app/build.gradle.kts`
- `android/app/src/main/java/top/akadesk/app/MainActivity.kt`

当前尚未落地但本次选型已经明确的部分：

- `desktop/` 的 Tauri 2 工程
- `host/` 的 Windows Host Core
- `proto/` 的跨端协议层

这意味着接下来的实现顺序不应该是“先把所有端都起起来”，而应该先补基础骨架，再做最短闭环。

## 8. 实施顺序建议

第一阶段：

- 固化 Android 基线
- 创建 Tauri 2 桌面壳
- 创建 Windows Host Core Rust workspace
- 建立 `proto/` 协议仓内基线

第二阶段：

- 跑通局域网发现
- 跑通配对和握手
- 跑通单路视频预览

第三阶段：

- 接入音频
- 接入输入注入
- 接入文件传输
- 补诊断和日志链路

第四阶段：

- 做稳定性、断线重连、码率/分辨率切换
- 视需要接入 Tailscale/Headscale 等用户自有组网方案

## 9. 本次结论

本次重启后的主路线固定为：

- Android：`原生 Kotlin + Compose`
- 桌面：`Tauri 2 + Vue 3 + TypeScript`
- Windows 被控核心：`Rust`
- 跨端共享：`Protocol Buffers`
- 媒体传输：`WebRTC`

这条路线的重点不是“所有端都统一语言”，而是“高频核心收敛在 Rust，UI 端各自选最合适的实现，跨端靠协议对齐”。
