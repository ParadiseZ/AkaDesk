# AkaDesk 技术选型

## 1. 文档目的

本文档用于作为 AkaDesk 远程控制项目重启后的技术基线，先把 V1 的平台范围、核心栈、模块边界和暂不采用的方案固定下来，避免后续边做边改。

当前结论以仓库现状为基础：

- `android/` 已经是可构建的 Android 原生工程。
- `desktop/` 目录当前还没有形成可运行桌面端实现。
- 桌面采用 `Tauri 2`
- Windows Host Runtime 默认按独立进程设计，由 Tauri 桌面壳负责拉起、监控和交互

## 2. V1 产品范围

V1 只做最核心闭环：

- Android 作为主控端
- Windows 作为被控端
- 局域网发现与直连
- 基础画面传输
- 基础音频传输
- 基础输入控制

V2 增量范围：

- 基础文件传输
- 文件传输记录和断点续传策略
- 传输队列、冲突处理、覆盖策略

V1 不优先投入：

- iOS / Linux 客户端
- 自建 NAT 穿透基础设施
- 复杂云中继
- 重型后台管理系统

## 3. 选型总览

| 领域 | 选型 | 结论 |
| --- | --- | --- |
| Android 主控端 | Kotlin + Jetpack Compose + Material 3 | 继续沿用，和当前仓库一致 |
| 桌面端 UI | Tauri 2 + TypeScript + Vue 3 | 作为 Windows 桌面壳和运维入口 |
| Windows Host Runtime | Rust | 负责本地运行时、会话编排、状态管理和 IPC 接入 |
| 平台实现层 | Rust trait + 平台适配实现 | 负责实际调用 Windows/Linux 平台接口 |
| 共享协议 | Protocol Buffers + 明确版本字段 | 跨语言共享层                               |
| 控制平面 | HTTP/WebSocket + 局域网发现 | 用于发现、配对、状态同步和协议控制 |
| 数据平面 | WebRTC | 用于低延迟视频、音频、DataChannel 输入事件 |
| 本地 IPC | 长连接二进制 IPC + Proto 消息 | 用于 Tauri 壳和 Host Runtime 之间通信 |
| Android 本地存储 | DataStore | 保存连接历史、偏好设置、输入配置 |
| 桌面状态存储 | Tauri Store 或 SQLite | 只保存本地配置、最近设备、诊断信息 |
| Windows 原生能力 | Rust crate + 必要的 Windows API 封装 | 高频能力不放在 WebView 层 |
| 构建基线 | Android: AGP 9.2.1 + Gradle 9.5.1 + Kotlin 2.3.21 | 已在当前仓库验证可构建 |

## 4. 为什么这样选

### 4.1 Android 继续原生

Android 主控端对触控、手柄、键鼠映射、前后台切换、音视频播放、权限模型都比较敏感。原生 Kotlin + Compose 的收益很明确：

- 输入和媒体能力接入成本最低
- Compose 更适合快速迭代遥控器、设备列表、悬浮控件等 UI
- 与当前仓库已存在的 `android/` 工程连续，不需要推倒重来

### 4.2 桌面端 Tauri 2

桌面端不是高频媒体渲染核心，而是宿主壳、配置入口、诊断入口和安装分发入口，因此 Tauri 2 更合适：

- 包体小，资源占用比 Electron 更稳
- Rust 后端更容易和 Windows 被控核心共用部分底层能力
- 前端 UI 迭代效率高，适合做设备管理、设置页、日志页、诊断页
- 如果后续需要托盘、开机自启、权限引导、文件选择、窗口管理，Tauri 2 都更顺手

桌面端这里不承担高频采集/编码主循环。真正的高频能力下沉到独立的 Host Runtime，而具体平台 API 调用再由更下层的 Platform Adapter 负责。

### 4.3 Host Runtime 运行模型

默认方案：

- `Tauri 主进程` 负责桌面壳、设置页、诊断页、托盘、日志展示
- `Rust Host Runtime` 作为单独进程运行
- Tauri 负责拉起、停止、重启、状态探测和日志桥接

这样设计的原因：

- 媒体采集、编码、输入注入是高频长生命周期任务，不适合和 UI 壳绑死
- Host Runtime 崩溃时只重启 Host，不连带打掉整个桌面壳
- 后续如果要做开机自启、后台常驻、Windows Service 或无界面运行，更容易演进
- Tauri UI 关闭后，未来仍可按策略保留 Host 常驻能力
- 能把权限、线程模型、实时链路和 WebView/UI 生命周期彻底隔离

### 4.4 本地 IPC 选型

默认方案：

- `Tauri 主进程 <-> Host Runtime` 使用长连接本地 IPC
- 消息格式统一使用 `Protocol Buffers`
- 传输层抽象为 `IpcTransport`
- Windows 默认实现：`Named Pipe`
- Linux 预留实现：`Unix Domain Socket`

为什么不把本地 IPC 直接定成 `localhost HTTP/WebSocket`：

- 会引入端口占用和端口探测问题
- 本地管理面没有必要暴露 TCP 监听口
- 以后接 Windows Service 或无界面常驻时，Named Pipe / UDS 更自然
- 同一套 Proto 消息可以直接复用，不需要再包一层 HTTP JSON

为什么不优先用 `stdio`：

- 适合短命 sidecar，不适合长期双向状态同步
- 做日志、事件推送、重连、探活时比较别扭
- 以后如果 Host 独立成服务，stdio 不好延续

结论：

- `V1` 本地 IPC 选 `Named Pipe + Protobuf`
- `Linux` 目标保持同一抽象，落地成 `Unix Domain Socket + Protobuf`

### 4.5 Host Runtime 和 Platform Adapter 的职责分离

必须拆成两层：

- `Host Runtime`
- `Platform Adapter`

`Host Runtime` 不直接写 Windows API，也不直接承担“某平台能力怎么调”的细节。它的职责是：

- 进程生命周期管理
- 会话状态机
- 连接调度
- 能力协商
- 日志、诊断、错误归一化
- 对上提供统一的 IPC 服务接口
- 调用抽象平台接口，而不是调用某个具体平台 API

`Platform Adapter` 才负责实际平台调用。它的职责是：

- 屏幕采集
- 系统音频采集
- 输入注入
- 窗口/显示器枚举
- 剪贴板、文件系统等平台能力
- 对接 Win32 / Linux 系统接口或第三方原生库

中间必须有一层平台抽象契约，例如：

- `ScreenCapturePort`
- `AudioCapturePort`
- `InputInjectionPort`
- `WindowEnumerationPort`
- `FileTransferPort`

这样上层 Runtime 调的永远是抽象端口，Windows 只是一套实现，未来可以再补 Linux 实现。

### 4.6 协议共享

- 用 `proto/` 维护跨端协议
- Kotlin、Rust、TypeScript 分别生成或映射各自模型
- 协议里强制保留 `version`、`capabilities`、`codec`、`feature flags`

这样更适合 Android + Tauri + Rust Host 的多语言组合，也更利于后续独立升级。

## 5. 分层设计建议

### 5.1 Android 主控端

建议职责：

- 设备发现
- 配对与连接
- 视频/音频播放
- 触控/按键/手柄输入
- 输入方案配置和偏好设置
- V2 再补文件上传下载入口

建议技术：

- `Kotlin`
- `Jetpack Compose`
- `Material 3`
- `Navigation Compose`
- `DataStore`
- 官方 Android WebRTC SDK

不建议现在就引入很重的架构层或过度 DI。V1 优先把连接、画面、输入闭环跑通。

### 5.2 Tauri 2 桌面端

建议职责：

- Windows 宿主 UI
- 本地服务状态展示
- 局域网可见性和配对入口
- 编码/采集能力诊断
- 日志查看、导出和故障引导
- 基础设置
- V2 再补文件传输记录和传输任务面板

建议技术：

- `Tauri 2`
- `Rust`
- `Vue 3`
- `TypeScript`
- `Vite`

选择 Vue 3 的原因很简单：做设置面板、设备列表、诊断页这类中后台式界面足够快，也方便和 Tauri 命令边界保持清晰。

### 5.3 Host Runtime

建议职责：

- 进程生命周期管理
- IPC 服务入口
- 会话保活、断线重连、能力协商
- 统一错误模型、日志、诊断事件
- 编排屏幕采集、音频采集、输入注入等抽象能力
- V2 再补文件收发能力

建议技术：

- `Rust`
- `tokio`
- `protobuf/prost`
- 平台抽象 trait
- 按平台注入具体实现

这里要坚持一个原则：`Host Runtime` 不直接耦合 Windows API。

### 5.4 Platform Adapter

建议职责：

- 屏幕采集
- 系统音频采集
- H.264 / HEVC(H.265)/ VP8/VP9/AV1 视频编码策略接入
- Opus 音频编码接入
- 输入注入
- 窗口、显示器、音频设备枚举
- V2 再补文件系统和文件传输底层能力

建议技术：

- `Rust`
- Windows/Linux 原生 API 封装
- WebRTC 传输栈
- 必要时引入独立原生库处理高频编解码

这里要坚持一个原则：平台相关实际调用只出现在 Adapter 层，不上浮到 Runtime，更不上浮到 Tauri 前端。

### 5.5 协议与会话层

建议拆成两层：

- 控制平面：设备发现、握手、配对、心跳、状态同步
- 数据平面：视频、音频、输入事件

建议：

- 局域网发现使用 `mDNS` 或受控 UDP 广播
- 控制平面优先走 `WebSocket`
- 数据平面优先走 `WebRTC`
- V2 文件传输优先走独立传输通道，不先塞进 V1 媒体主链路

这样做的好处是 UI 改动、设置页改动、发现逻辑改动，不会轻易影响到媒体链路。

说明：

- `proto/` 放跨端协议定义
- Android 不直接复用 Tauri 或 Rust UI 层，只复用协议

## 7. 当前仓库对应关系

当前已经落地的只有 Android 基线：

- `android/settings.gradle.kts`
- `android/build.gradle.kts`
- `android/app/build.gradle.kts`
- `android/app/src/main/java/top/akadesk/app/MainActivity.kt`

当前尚未落地但本次选型已经明确的部分：

- `desktop/` 的 Tauri 2 工程
- `desktop/host/` 下的 Host Runtime、IPC 和平台抽象层
- `desktop/host/windows/` 下的 Windows Adapter 实现
- `proto/` 的跨端协议层

这意味着接下来的实现顺序不应该是“先把所有端都起起来”，而应该先补基础骨架，再做最短闭环。

## 8. 三方包策略

默认原则：

- 有成熟三方包的能力先用三方包
- 三方包不够时，再在外面包一层自己的薄封装
- 只有三方包能力缺口明显时，才直接下沉到 Windows 原生 API 细节

这条原则尤其适用于：

- Proto 生成和校验
- Tauri 插件
- 异步运行时
- 日志、错误、配置
- Windows 平台能力

## 9. 候选三方包清单

### 9.1 协议与代码生成

优先采用：

- `protobuf` / `protoc`
- `buf`
- TypeScript 生成：`@bufbuild/protobuf` + `protoc-gen-es`
- Rust 生成：`prost` + `prost-build`
- Android 生成：`protoc --java_out + --kotlin_out`

用途：

- `buf` 负责格式化、lint、breaking change 检查和统一生成入口
- TypeScript 侧优先走 Buf 的 ES 生成链，减少手搓 codec
- Rust 侧优先用 `prost`，先解决消息结构和演进问题
- Android 侧直接使用 Kotlin/Java 生成代码，不手写 DTO

协议字段约定：

- 所有握手和状态消息都带 `version`
- 能力协商消息带 `capabilities`
- 媒体相关消息带 `codec`、`profile`、`transport`
- 能做增量演进的地方优先用新增字段，不直接重命名旧字段

### 9.2 Android 主控端

优先采用：

- `androidx.activity:activity-compose`
- `androidx.compose.material3`
- `androidx.navigation:navigation-compose`
- `androidx.datastore`
- `androidx.lifecycle`
- `kotlinx-coroutines-android`
- 官方 Android WebRTC SDK

待接入时确认：

- 如需图片加载，再加 `coil-compose`

建议：

- Android 端先尽量薄，不要过早引入重量级 DI
- 连接、媒体、输入闭环先跑通，再补更重的状态管理和模块拆分

### 9.3 Tauri 2 桌面壳

优先采用：

- `tauri`
- `vue`
- `vue-router`
- `pinia`
- `vite`

Tauri 官方插件优先采用：

- `@tauri-apps/plugin-dialog`
- `@tauri-apps/plugin-fs`
- `@tauri-apps/plugin-log`
- `@tauri-apps/plugin-store`
- `@tauri-apps/plugin-process`
- `@tauri-apps/plugin-opener`
- `@tauri-apps/plugin-updater`
- `@tauri-apps/plugin-notification`

按需采用：

- `@tauri-apps/plugin-shell`

建议：

- `shell` 只在确实需要启动 sidecar 或受控外部命令时再开
- 能走官方插件的能力，不自己绕系统命令

### 9.4 Rust Host Runtime

优先采用：

- `tokio`
- `anyhow`
- `thiserror`
- `tracing`
- `tracing-subscriber`
- `serde`
- `serde_json`
- `bytes`
- `tokio-util`
- `windows`
- `interprocess`

网络与发现候选：

- `tokio-tungstenite` 或其他成熟 WebSocket crate
- `mdns-sd` 作为局域网发现候选

媒体与实时链路候选：

- 先评估现成 Rust WebRTC crate
- 如果现成 crate 在性能、编码控制、平台能力接入上不够，再评估直接接原生 `libwebrtc`

平台能力策略：

- 屏幕采集优先找成熟 crate
- 系统音频采集优先找成熟 crate
- 输入注入优先找成熟 crate
- 如果以上任一能力在 Windows 上不稳，再直接基于 `windows` crate 封装 DXGI / WASAPI / SendInput

不建议一开始就为了“纯原生可控”把所有能力从零手写。

本地 IPC 策略：

- Windows 优先评估 `Named Pipe`
- Linux 目标预留 `Unix Domain Socket`
- Rust 侧先找成熟 IPC crate；不够时再在 `tokio` 上自己封装
- IPC 消息体统一使用 Proto，避免本地再搞一套 JSON DTO

### 9.5 V2 文件传输候选

优先采用：

- 控制面元数据仍走现有协议层
- 传输流优先单独建通道
- 大文件传输时优先考虑分块、校验和、重试

Rust 侧可能会用到：

- `sha2`
- `tokio::fs`
- `tokio-util`

如果 V2 真做断点续传，再补：

- 分块编号
- 续传游标
- 目标端冲突策略
- 文件哈希校验

## 10. 实施顺序建议

第一阶段：

- 固化 Android 基线
- 创建 Tauri 2 桌面壳
- 创建 `desktop/host/` Runtime + contracts + ipc
- 创建 `desktop/host/windows/` Adapter workspace
- 建立 `proto/` 协议仓内基线

第二阶段：

- 跑通局域网发现
- 跑通配对和握手
- 跑通单路视频预览

第三阶段：

- 做稳定性、断线重连、码率/分辨率切换
- 接入音频
- 接入输入注入
- 补诊断和日志链路

第四阶段：
- 接入 V2 文件传输
- 视需要接入 Tailscale/Headscale 等用户自有组网方案

## 11. 本次结论

本次重启后的主路线固定为：

- Android：`原生 Kotlin + Compose`
- 桌面：`Tauri 2 + Vue 3 + TypeScript`
- Windows 被控核心：`Rust`
- 跨端共享：`Protocol Buffers`
- 媒体传输：`WebRTC`

这条路线的重点不是“所有端都统一语言”，而是“高频核心收敛在 Rust，UI 端各自选最合适的实现，跨端靠协议对齐”。
