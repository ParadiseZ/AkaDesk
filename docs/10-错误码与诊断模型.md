# AkaDesk 错误码与诊断模型

## 1. 文档目的

本文档用于固定 AkaDesk V1 的：

- 错误码分段
- 错误结构
- 断开原因与错误的关系
- 诊断事件模型
- 日志等级与落盘范围
- 状态快照与诊断快照边界
- 用户可见错误提示策略

本文档只定义模型和规则，不展开代码实现。

## 2. 文档位置

本文档固定放在：

- `docs/10-错误码与诊断模型.md`

## 3. 目标

错误与诊断模型必须同时满足：

1. 用户看得懂
2. 程序可分类处理
3. 日志可检索
4. 状态可复盘
5. 不把平台原始错误直接泄漏到 UI

## 4. 设计原则

### 4.1 错误码不是错误消息

必须区分：

- `code`
- `message`
- `detail`

建议语义：

- `code`
  - 稳定、可枚举、可检索
- `message`
  - 面向用户
- `detail`
  - 面向日志和诊断

### 4.2 断开原因和错误对象分开

必须区分：

- 为什么会话结束
- 过程中具体出了什么错

例如：

- `DISCONNECT_REASON_RUNTIME_ERROR`
- `MEDIA_ENCODER_UNAVAILABLE`

这两个概念不能混成一个字段。

### 4.3 诊断事件不是日志文本

诊断事件应是结构化对象，不是纯字符串。

这样后面才能支持：

- UI 过滤
- 搜索
- 导出
- 聚合统计

### 4.4 用户提示优先稳定，不优先完整

UI 展示优先给稳定、短句、可执行建议。

不要把：

- Win32 原始错误
- 第三方库原始错误
- 栈追踪

直接暴露给普通用户。

## 5. 基础错误结构

当前协议里已有：

```proto
message ErrorInfo {
  string code = 1;
  string message = 2;
  bool retryable = 3;
  string detail = 4;
}
```

V1 建议继续沿用这四个基础字段。

建议语义固定为：

| 字段 | 含义 |
| --- | --- |
| `code` | 稳定错误码 |
| `message` | 面向用户的错误摘要 |
| `retryable` | 当前操作是否建议允许重试 |
| `detail` | 面向日志、诊断和导出的详细信息 |

## 6. 错误码分段

V1 错误码分段建议固定为：

| 范围 | 前缀 | 含义 |
| --- | --- | --- |
| `1000-1099` | `DISCOVERY_` | 发现失败 |
| `1100-1199` | `PAIRING_` | 配对失败 |
| `1200-1299` | `AUTH_` | 认证失败 |
| `1300-1399` | `SESSION_` | 会话建立/切换失败 |
| `1400-1499` | `MEDIA_` | 视频音频协商或链路失败 |
| `1500-1599` | `INPUT_` | 输入处理失败 |
| `1600-1699` | `DISPLAY_` | 显示器设置失败 |
| `1700-1799` | `IPC_` | 本地 IPC 失败 |
| `1800-1899` | `RUNTIME_` | Host Runtime 内部错误 |
| `1900-1999` | `DIAGNOSTIC_` | 诊断与导出失败 |

约束：

- 每个错误码只能归属一个前缀
- 不要让同一错误同时出现两个业务归类

## 8. `retryable` 规则

V1 建议把错误分成三种重试语义：

1. 可直接重试
2. 修正后重试
3. 不建议立即重试

建议映射：

- `DISCOVERY_TIMEOUT`
  - `retryable = true`
- `PAIRING_CODE_INVALID`
  - `retryable = true`
- `AUTH_TOKEN_INVALID`
  - `retryable = false`
- `DISPLAY_MODE_UNSUPPORTED`
  - `retryable = false`
- `MEDIA_ENCODER_UNAVAILABLE`
  - 若存在软编回退路径，可视为 `true`
  - 否则 `false`

## 9. 断开原因模型

当前至少保留：

- `DISCONNECT_REASON_CONTROLLER_REQUEST`
- `DISCONNECT_REASON_CONTROLLED_REQUEST`
- `DISCONNECT_REASON_NETWORK_LOST`
- `DISCONNECT_REASON_HEARTBEAT_TIMEOUT`
- `DISCONNECT_REASON_RUNTIME_ERROR`

建议补齐到 V1 正式枚举的还有：

- `DISCONNECT_REASON_MEDIA_ERROR`
- `DISCONNECT_REASON_DISPLAY_APPLY_FAILED`
- `DISCONNECT_REASON_AUTH_REVOKED`

## 9.1 使用原则

- `DisconnectReason` 表达“为什么会话结束”
- `ErrorInfo` 表达“具体错误是什么”
- 一个断开事件可以只有 `reason`
- 也可以同时带 `reason + error`

例如：

- 用户主动断开
  - `reason = DISCONNECT_REASON_CONTROLLER_REQUEST`
  - `error = null`

- 编码器初始化失败导致断开
  - `reason = DISCONNECT_REASON_MEDIA_ERROR`
  - `error.code = MEDIA_ENCODER_UNAVAILABLE`

## 10. 诊断事件模型

V1 建议正式引入：

- `DiagnosticEvent`

建议它至少具备这些字段：

| 字段 | 含义 |
| --- | --- |
| `event_id` | 事件唯一标识 |
| `timestamp_ms` | 事件时间 |
| `level` | 严重级别 |
| `category` | 事件分类 |
| `code` | 对应错误码或事件码 |
| `session_id` | 关联会话，可空 |
| `message` | 面向用户或运维的摘要 |
| `detail` | 结构化或半结构化细节 |

## 10.1 `level` 建议枚举

- `DEBUG`
- `INFO`
- `WARN`
- `ERROR`

## 10.2 `category` 建议枚举

- `DISCOVERY`
- `PAIRING`
- `AUTH`
- `SESSION`
- `MEDIA`
- `INPUT`
- `DISPLAY`
- `IPC`
- `RUNTIME`
- `DIAGNOSTIC`

## 10.3 典型事件

- 发现开始
- 发现完成
- 配对请求发起
- 配对成功
- 配对失败
- 会话进入 `NEGOTIATING`
- 会话进入 `STREAMING`
- 进入 `DEGRADED`
- 编码器从硬编回退软编
- 显示器模式恢复成功
- 显示器模式恢复失败
- 音频输出设置恢复成功
- 音频输出设置恢复失败
- IPC 断开

## 11. 日志模型

日志和诊断事件有关联，但不是一回事。

建议关系：

- 结构化诊断事件用于 UI、导出、筛选
- 文本日志用于开发调试和原始追踪

## 11.1 日志等级

建议保留：

- `TRACE`
- `DEBUG`
- `INFO`
- `WARN`
- `ERROR`

V1 UI 默认展示：

- `INFO`
- `WARN`
- `ERROR`

## 11.2 落盘范围

V1 不建议默认长期保存：

- 所有原始视频统计点
- 高频输入事件原文
- 全量帧级诊断

V1 建议可保留：

- 最近一次会话摘要
- 最近一次错误摘要
- 最近一次降级事件
- 最近一次显示器恢复结果
- 最近一次音频输出设置恢复结果

## 12. 诊断快照模型

除了事件流，V1 还建议保留诊断快照：

- `RuntimeStatusSnapshot`
- `CapabilitySnapshot`
- `SessionSnapshot`
- `DiagnosticSnapshot`

其中：

- `RuntimeStatusSnapshot`
  - 当前 Runtime 生命周期状态
- `CapabilitySnapshot`
  - 当前平台能力摘要
- `SessionSnapshot`
  - 当前或最近会话状态摘要
- `DiagnosticSnapshot`
  - 最近错误、最近警告、最近降级、最近恢复结果

## 12.1 `DiagnosticSnapshot` 建议字段

- `last_error`
- `last_warning`
- `last_degraded_event`
- `last_display_restore_result`
- `last_audio_restore_result`
- `last_session_closed_event`
- `updated_at_ms`

## 13. 用户可见错误模型

V1 UI 不直接显示 `detail`。

建议 UI 侧错误项至少包含：

- `title`
- `message`
- `suggested_action`
- `retryable`

例如：

- `DISPLAY_MODE_UNSUPPORTED`
  - `title`: 显示器设置失败
  - `message`: 目标分辨率或刷新率不被被控端支持
  - `suggested_action`: 请选择被控端支持的分辨率、缩放和帧率后重试

- `AUTH_TOKEN_REVOKED`
  - `title`: 配对已失效
  - `message`: 当前设备的配对凭证已被撤销
  - `suggested_action`: 请重新完成配对

- `MEDIA_DECODER_UNAVAILABLE`
  - `title`: 视频无法正常播放
  - `message`: 当前设备无法使用该视频解码方式
  - `suggested_action`: 请手动调整分辨率、码率或帧率后重试

## 14. 导出与排障

V1 建议支持导出：

- 会话摘要
- 最近诊断事件
- 最近错误与告警
- 当前平台能力摘要
- 当前显示器模式与 `history_display_mode`

不建议默认导出：

- 长时间完整文本日志
- 原始媒体数据

## 15. 与现有状态机的关系

错误与状态的关系建议固定为：

- 可恢复异常
  - `RuntimeState -> DEGRADED`
  - `SessionState` 可保持 `STREAMING`

- 不可恢复异常
  - `SessionState -> FAILED`
  - `RuntimeState -> ERROR` 或清理后回 `READY`

- 主动断开
  - 不产生错误码
  - 只产生 `DisconnectReason`

## 16. V1 最小闭环要求

开始开发时，第一批必须先落下来的最小集合：

1. `ErrorInfo`
2. `DisconnectReason`
3. 错误码分段
4. 第一批错误码清单
5. `DiagnosticEvent`
6. `DiagnosticSnapshot`
7. 用户可见错误映射

## 17. 本次结论

错误码与诊断模型文档固定放在：

- `docs/10-错误码与诊断模型.md`

它定的是：

- 错误码怎么分段
- 断开原因和错误怎么分开
- 诊断事件和日志怎么分工
- 哪些信息该给用户看，哪些只该进日志

后续如果继续，最自然的动作就是把这里的 `ErrorInfo`、`DiagnosticEvent`、错误码枚举和 UI 错误映射收敛回 `proto/`、`contracts/error/` 和桌面端诊断页模型。
