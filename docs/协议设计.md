# AkaDesk 协议设计

## 1. 文档目的

本文档定义 AkaDesk V1 的协议边界和消息设计，服务于三个目标：

- 明确控制面、数据面、本地 IPC 的职责边界
- 明确跨端消息类型、方向、时序和失败处理
- 为后续 `proto/` 文件落地提供直接依据

本文档只写协议，不写代码实现。

## 2. 文档位置与代码落位

本文档文件位置：

- `docs/协议设计.md`

后续协议代码落位：

- 跨端共享协议：`proto/`
- 本地 IPC 协议：`proto/ipc.proto`
- Host Runtime 领域映射：`desktop/host/contracts/`

建议协议文件拆分：

- `proto/common.proto`
- `proto/device.proto`
- `proto/session.proto`
- `proto/media.proto`
- `proto/input.proto`
- `proto/ipc.proto`

## 3. 协议分层

当前项目的协议分三层：

| 层 | 通道 | 作用 |
| --- | --- | --- |
| 发现层 | `mDNS` | 局域网内发现设备、拿到控制入口 |
| 控制层 | `WebSocket + Protobuf` | 配对、握手、心跳、会话建立、状态同步、输入命令 |
| 数据层 | `WebRTC` | 视频、音频、DataChannel 输入 |
| 本地 IPC 层 | `interprocess + Protobuf` | `Tauri Shell <-> Host Runtime` 本地管理通信 |

约束：

- `Tauri Shell` 不直接参与远程媒体流
- 视频、音频帧不进入本地 IPC
- 远程输入默认优先走 `WebRTC DataChannel`
- 本地 IPC 只承载控制、状态、诊断、配置

## 4. 协议总原则

### 4.1 一条消息只做一类事情

避免把这些混在一个大消息里：

- 发现
- 配对
- 会话建立
- 状态推送
- 诊断事件

### 4.2 请求和事件分开

控制层和 IPC 层都要区分：

- `Request`
- `Response`
- `Event`

这样前端和 Runtime 都更容易做超时、重试和日志追踪。

### 4.3 所有状态消息都可快照化

不要只发“增量动作”，要保留快照消息，例如：

- `DeviceSnapshot`
- `SessionSnapshot`
- `RuntimeStatusSnapshot`

这样 UI 或新连接方可以直接同步当前状态，而不是只能靠事件回放恢复。

### 4.4 V1 先只落 H.264 视频协议主线

媒体协商结构要预留多 codec，但 V1 只正式落：

- `VIDEO_CODEC_H264`
- `AUDIO_CODEC_OPUS`

HEVC、VP8、VP9、AV1 只保留协议扩展位，不作为 V1 必须实现项。

## 5.2 `proto/device.proto`

- `DeviceIdentity`
- `DevicePresence`
- `DeviceSnapshot`
- `DisplayInfo`
- `AudioDeviceInfo`

用途：

- 设备发现
- 设备列表展示
- 连接前能力摘要

## 5.3 `proto/media.proto`

放这些内容：

- `VideoCodec`
- `AudioCodec`
- `CodecImplementation`
- `VideoPreference`
- `AudioPreference`
- `VideoSessionSpec`
- `AudioSessionSpec`

用途：

- 主控媒体偏好
- 会话协商结果
- 实际运行参数快照

## 5.4 `proto/session.proto`

放这些内容：

- `SessionIntent`
- `SessionNegotiationResult`
- `SessionSnapshot`

用途：

- 会话建立
- 会话状态同步

## 5.5 `proto/input.proto`

放这些内容：

- `InputEvent`

## 5.6 `proto/ipc.proto`

放这些内容：

- `IpcEnvelope`

- `Tauri Shell <-> Host Runtime` 管理面通信

## 6. 发现协议

## 6.1 目标

发现阶段只解决两件事：

- Android 主控能发现被控设备
- 主控能拿到后续控制连接入口和基础摘要

发现协议不做：

- 配对确认
- 会话建立
- 媒体协商

## 6.2 发现结果最小字段

发现响应至少包含：

- `device_id`
- `display_name`
- `platform`
- `hostname`
- `app_version`
- `control_address`
- `control_port`
- `paired`
- `reachable`
- `last_seen_ms`

建议直接复用：

- `DevicePresence`

## 6.3 发现消息

### `DiscoveryProbe`

方向：

- `Android Controller -> LAN`

作用：

- 广播或查询当前局域网可见被控设备

最小字段：

- `request_id`
- `version`

### `DiscoveryAnnounce`

方向：

- `Controlled Host -> LAN`

作用：

- 返回自己可被连接的入口摘要

最小字段：

- `DevicePresence`

## 6.4 发现阶段约束

- 未配对设备可以被发现
- 但未配对设备只暴露最小必要信息
- 详细平台能力快照通过后续控制层拉取

## 7. 配对与认证协议

## 7.1 V1 范围

V1 只做局域网内配对，不引入复杂账号系统。

目标：

- 主控和被控建立可信关系
- 后续重连不需要重复人工确认

## 7.2 配对模型

建议模型：

- 被控端维护本地 `paired_controllers`
- 每个主控设备有独立 `controller_device_id`
- 配对成功后保存 `pair_token` 或等价凭证摘要

## 7.3 配对消息

### `PairingRequest`

方向：

- `Android Controller -> Controlled Host`

作用：

- 请求建立配对关系

最小字段：

- `request_id`
- `controller_device_id`
- `controller_display_name`
- `version`

### `PairingChallenge`

方向：

- `Controlled Host -> Android Controller`

作用：

- 要求主控输入或确认一次性配对码，或等待被控本地确认

最小字段：

- `request_id`
- `challenge_id`
- `challenge_type`
- `expires_at_ms`

### `PairingConfirm`

方向：

- `Android Controller -> Controlled Host`

作用：

- 提交配对码或确认挑战

最小字段：

- `request_id`
- `challenge_id`
- `verification_code`

### `PairingResult`

方向：

- `Controlled Host -> Android Controller`

作用：

- 返回配对是否成功

最小字段：

- `request_id`
- `accepted`
- `pair_token`
- `error`

## 7.4 配对后认证

后续控制连接应携带：

- `controller_device_id`
- `pair_token`
- `version`

建议统一放入：

- `ControlHello`

未携带或校验失败时：

- 返回认证失败错误
- 不进入会话协商阶段

## 8. 控制连接与握手协议

## 8.1 控制连接目标

控制连接用于：

- 鉴权
- 拉取能力摘要
- 发起会话
- 推送状态
- 推送断开与错误

## 8.2 握手消息

### `ControlHello`

方向：

- `Android Controller -> Controlled Host`

作用：

- 建立控制层逻辑会话

最小字段：

- `request_id`
- `controller_device_id`
- `pair_token`
- `version`
- `supported_features`

### `ControlHelloAck`

方向：

- `Controlled Host -> Android Controller`

作用：

- 返回认证结果和被控摘要

最小字段：

- `request_id`
- `accepted`
- `DeviceIdentity`
- `CapabilityFlags`
- `error`

### `GetDeviceSnapshot`

方向：

- `Android Controller -> Controlled Host`

作用：

- 请求连接前能力快照

### `DeviceSnapshotResponse`

方向：

- `Controlled Host -> Android Controller`

作用：

- 返回完整 `DeviceSnapshot`

## 8.3 心跳消息

### `HeartbeatPing`

方向：

- 双向

### `HeartbeatPong`

方向：

- 双向

作用：

- 检查控制连接是否仍然可用

最小字段：

- `request_id`
- `timestamp_ms`

超时策略：

- 连续超时达到阈值，触发 `DISCONNECT_REASON_HEARTBEAT_TIMEOUT`

## 9. 会话建立协议

## 9.1 会话目标

从主控提出远控意图，到双方拿到稳定会话参数。

## 9.2 主消息

### `StartSessionRequest`

方向：

- `Android Controller -> Controlled Host`

作用：

- 请求建立远控会话

载荷建议直接复用：

- `SessionIntent`

### `StartSessionAccepted`

方向：

- `Controlled Host -> Android Controller`

作用：

- 表示会话已进入准备或协商阶段

最小字段：

- `session_id`
- `state`

### `SessionChangedEvent`

方向：

- `Controlled Host -> Android Controller`

作用：

- 推送会话状态变化

载荷建议：

- `SessionSnapshot`

### `StartSessionRejected`

方向：

- `Controlled Host -> Android Controller`

作用：

- 会话建立前就被拒绝

最小字段：

- `session_id`
- `error`

## 9.3 会话建立约束

- `session_id` 由被控端生成
- 被控端在 `NEGOTIATING` 之前必须完成基本认证
- 被控端在 `PREPARING` 之前必须拿到明确的视频/音频偏好
- UI 展示优先依赖 `SessionSnapshot`，不要自己拼状态

## 10. 媒体协商协议

## 10.1 当前最终口径

当前项目的视频协商固定遵守：

- 主控端下发目标视频编码信息
- 被控端按协商结果输出对应编码的视频流
- 主控端优先使用该编码的硬解
- 主控端不支持该编码硬解时，回退到同编码软解
- V1 先只实现 `H.264`

音频当前固定：

- `AUDIO_CODEC_OPUS`

## 10.2 协商消息

### `MediaPreferenceOffer`

方向：

- `Android Controller -> Controlled Host`

作用：

- 提交本次会话媒体偏好

载荷建议：

- `VideoPreference`
- `AudioPreference`

### `MediaNegotiationResult`

方向：

- `Controlled Host -> Android Controller`

作用：

- 返回最终媒体参数

载荷建议：

- `SessionNegotiationResult`

## 10.3 V1 必须支持的协商字段

视频：

- `codec`
- `width`
- `height`
- `fps`
- `bitrate_kbps`
- `allow_same_codec_software_fallback`

音频：

- `codec`
- `sample_rate`
- `channels`
- `bitrate_kbps`

运行中修改约束：

- `bitrate_kbps` 允许动态修改
- `fps` 允许动态修改
- 分辨率允许动态修改
- 这里的分辨率指目标显示器分辨率
- 分辨率修改允许按重配或重建链路处理
- 传输过程中不允许动态修改 `codec`

显示器模式变更语义：

- 分辨率修改请求应携带 `requested_display_mode`
- 被控端应保留 `history_display_mode`
- `history_display_mode` 至少包含：分辨率、缩放倍率、`fps/refresh_rate`
- 请求成功时，当前会话使用 `requested_display_mode`
- 请求失败时，保持 `history_display_mode`
- 会话断开时，必须恢复 `history_display_mode`

## 10.4 WebRTC 建立消息

建议不再自定义一套 SDP 语义，只把它当作控制层交换载荷。

### `WebRtcOffer`

方向：

- `Controlled Host -> Android Controller`

最小字段：

- `session_id`
- `sdp`

### `WebRtcAnswer`

方向：

- `Android Controller -> Controlled Host`

最小字段：

- `session_id`
- `sdp`

### `IceCandidate`

方向：

- 双向

最小字段：

- `session_id`
- `candidate`
- `sdp_mid`
- `sdp_mline_index`

## 11. 输入事件协议

## 11.1 通道

默认优先：

- `WebRTC DataChannel`

仅在必要时才考虑：

- 控制层补发

## 11.2 V1 输入范围

V1 先支持：

- 鼠标移动
- 鼠标按键
- 滚轮
- 键盘按键

后续再扩：

- 多指触控
- 手势
- 手柄输入

## 11.3 输入消息

输入结构直接复用：

- `InputEvent`

V1 关键字段：

- `session_id`
- `seq`
- `timestamp_ms`
- `normalized_x`
- `normalized_y`
- `key_code`
- `action`

约束：

- 每个输入事件带递增 `seq`
- 被控端按 `session_id` 路由到目标会话
- 坐标先统一用归一化值，不直接依赖分辨率像素

## 12. 断开协议

## 12.1 主控主动断开

### `StopSessionRequest`

方向：

- `Android Controller -> Controlled Host`

最小字段：

- `session_id`

### `SessionClosedEvent`

方向：

- `Controlled Host -> Android Controller`

最小字段：

- `session_id`
- `reason = DISCONNECT_REASON_CONTROLLER_REQUEST`

## 12.2 被控主动断开

### `StopSessionEvent`

方向：

- `Controlled Host -> Android Controller`

最小字段：

- `session_id`
- `reason = DISCONNECT_REASON_CONTROLLED_REQUEST`

## 12.3 异常断开

### `SessionClosedEvent`

方向：

- `Controlled Host -> Android Controller`

最小字段：

- `session_id`
- `reason`
- `error`

异常来源包括：

- 网络丢失
- 心跳超时
- 采集失败
- 编码失败
- 平台设备丢失
- Runtime 内部错误

## 13. 本地 IPC 协议

## 13.1 IPC 目标

`Tauri Shell <-> Host Runtime` 之间要完成：

- 拉起后状态同步
- 能力快照读取
- 会话管理
- 日志与诊断订阅
- 设置下发

## 13.2 IPC 封装

统一使用：

- `IpcEnvelope`

字段：

- `request_id`
- `kind`
- `type`
- `payload`
- `timestamp_ms`

说明：

- `type` 决定业务消息种类
- `payload` 内部仍然是具体 Proto 消息

## 13.3 第一批 IPC 消息类型

### 请求类

- `GetRuntimeStatus`
- `GetCapabilitySnapshot`
- `StartSession`
- `StopSession`
- `ApplyDisplaySettings`
- `GetDiagnostics`

### 响应类

- `RuntimeStatusResponse`
- `CapabilitySnapshotResponse`
- `StartSessionResponse`
- `StopSessionResponse`
- `ApplyDisplaySettingsResponse`
- `DiagnosticsResponse`

### 事件类

- `RuntimeStatusChanged`
- `CapabilitySnapshotChanged`
- `SessionChanged`
- `SessionClosed`
- `DiagnosticEvent`

## 13.4 IPC 约束

- IPC 不承载视频帧和音频帧
- IPC 中的状态类消息优先传快照，不只传局部 patch
- `Tauri Shell` 不直接操作平台 Adapter，只通过 Host Runtime

## 14. 错误码设计

## 14.1 目标

错误码必须同时满足：

- 用户可展示
- 程序可分类
- 日志可检索

## 14.2 错误码分段建议

| 范围 | 前缀 | 含义 |
| --- | --- | --- |
| `1000-1099` | `DISCOVERY_` | 发现失败 |
| `1100-1199` | `PAIRING_` | 配对失败 |
| `1200-1299` | `AUTH_` | 认证失败 |
| `1300-1399` | `SESSION_` | 会话建立/切换失败 |
| `1400-1499` | `MEDIA_` | 视频音频协商或链路失败 |
| `1500-1599` | `INPUT_` | 输入处理失败 |
| `1600-1699` | `DISPLAY_` | 显示器设置失败 |
| `1700-1799` | `IPC_` | 本地 IPC 失败 |
| `1800-1899` | `RUNTIME_` | Host Runtime 内部错误 |

## 14.3 V1 第一批错误码

- `DISCOVERY_TIMEOUT`
- `PAIRING_REJECTED`
- `PAIRING_CODE_INVALID`
- `AUTH_TOKEN_INVALID`
- `AUTH_TOKEN_EXPIRED`
- `SESSION_ALREADY_ACTIVE`
- `SESSION_INVALID_STATE`
- `MEDIA_CODEC_UNSUPPORTED`
- `MEDIA_DECODER_UNAVAILABLE`
- `MEDIA_ENCODER_UNAVAILABLE`
- `MEDIA_WEBRTC_NEGOTIATION_FAILED`
- `INPUT_INJECTION_FAILED`
- `DISPLAY_MODE_UNSUPPORTED`
- `IPC_CHANNEL_CLOSED`
- `RUNTIME_INTERNAL_ERROR`

要求：

- 所有错误都落到 `ErrorInfo.code`
- `message` 面向用户
- `detail` 面向日志和诊断

## 15. 断开原因枚举

V1 断开原因至少保留：

- `DISCONNECT_REASON_CONTROLLER_REQUEST`
- `DISCONNECT_REASON_CONTROLLED_REQUEST`
- `DISCONNECT_REASON_NETWORK_LOST`
- `DISCONNECT_REASON_HEARTBEAT_TIMEOUT`
- `DISCONNECT_REASON_RUNTIME_ERROR`

建议后续扩展：

- `DISCONNECT_REASON_MEDIA_ERROR`
- `DISCONNECT_REASON_DISPLAY_APPLY_FAILED`
- `DISCONNECT_REASON_AUTH_REVOKED`

## 17. 本次结论

协议设计文档固定放在：

- `docs/协议设计.md`

它解决的是“该发什么消息、谁发、什么时候发、失败怎么回”，不是“代码怎么写”。

下一步如果继续，最顺的就是把这里的 `V1 协议最小闭环` 转成真实 `proto/` 文件。
