# M5 电脑系统声音传到 Android

## 本轮范围

Windows 当前默认输出设备的 WASAPI 回环采集，经 FFmpeg libopus 编码，通过与 H.264 画面共用的 WebRTC 连接，送到 Android 解码播放。固定 48 kHz、双声道、20 ms 帧，默认 64 kbps。未增加麦克风采集、虚拟音频设备或音频传输开关。

手机底部提供“手机声音”和“电脑声音”两个按钮。手机静音仅调节收到的 AudioTrack 播放音量；电脑静音经 `SetAudioMuteRequest / SetAudioMuteResponse` 修改采集端点的静音状态。按钮等待返回结果，失败或超时显示可重试提示。

## 实现落点

- `desktop/host/windows/src/audio/wasapi.rs`：输出设备查询、回环 PCM、端点静音与恢复。COM 对象仅在音频工作线程使用。
- `desktop/host/windows/src/ffmpeg/mod.rs`：持续 Opus 编码，直接输出 WebRTC 所需的 Opus 包，不添加容器头。
- `desktop/host/runtime/src/audio/mod.rs`：有界采集队列、静音指令、停止和持久恢复记录。
- `desktop/host/runtime/src/transport/mod.rs`：Offer 内同时建立 sendonly H.264 与 Opus，通过 BUNDLE 共用连接。音频发送独立于视频接帧等待，超过缓存窗口的旧音频丢弃并补偿 RTP 时间戳。
- `proto/media.proto` 与 `proto/session.proto`：静音请求/响应、当前会话音频参数和电脑静音状态。请求沿用会话所有者校验。
- Android `AndroidWebRtcSession.kt`、`RemoteAudioOutput.kt`：recvonly 音频、双声道播放、音频焦点、本地静音、临时输出路由恢复。
- Android `ControlProtoCodec.kt`、`HostControlSession.kt`、`ControllerCoordinator.kt`：启动偏好、状态解析、静音结果、过期会话隔离和按钮状态。

Android 当前 WebRTC 库使用通话音频输出；播放期间由音量键控制该输出，结束时恢复此前的音量键控制流。应用不直接修改系统音量。无外接输出时临时使用扬声器，已有耳机输出时保留外接路由；蓝牙和耳机热插拔需另行实机验收。

## 恢复行为

在任何静音修改之前，`audio_restore.json` 原子记录原端点 ID、原静音状态和音量快照。正常断开、电脑主动断开、音频采集失败或连接终止均停止采集并恢复原端点的静音。应用不修改系统音量或默认输出设备，因此不重写这两项。

恢复成功后才删除记录；进程被终止后，下次 Host Runtime 启动或新音频会话开始前读取记录并尝试恢复。原设备已移除等导致的恢复错误保留记录并上报诊断。恢复只针对记录中的端点，不改后来切换的新默认输出设备。

WASAPI 默认回环位置位于端点音量和静音之前，因此电脑静音不会停止传给手机的声音。参考 [Microsoft 回环录音说明](https://learn.microsoft.com/en-us/windows/win32/coreaudio/loopback-recording) 与 [POST_VOLUME_LOOPBACK 定义](https://learn.microsoft.com/en-us/windows/win32/api/audioclient/ne-audioclient-audclnt_streamoptions)。

## 已验证

- Android Debug APK 与测试 APK 构建、26 项单元测试通过，涵盖控制消息、音频默认偏好、静音响应失败保留连接等行为。
- Windows Host 工作区 25 项测试通过，包括 IPC、发现配对、Host Runtime 和会话清理；音频队列在正常调度抖动时保持顺序，积压时有界，旧会话不能静音或停止当前采集。另显式运行 1 项真实 WASAPI 测试通过。Linux 本轮未验收。
- SDP 测试确认两个 sendonly 媒体、Opus 48000/2、双声道参数、BUNDLE 和实际 ICE MID。
- Opus 编码包经 FFmpeg 解码得到 960 帧非静音双声道音频。
- 本机真实 WASAPI 测试音：未静音与电脑静音时 PCM 峰值均为 0.088378906；正常结束和模拟持久恢复记录都恢复原静音，原音量保持一致。
- realme RMX5060 真机通过静音场景和 440 Hz 系统测试音场景：测试音场景收到 30 个 Opus 包、6272 字节，`totalSamplesReceived=36320`，`totalAudioEnergy=0.004134186845212148`，Android 播放输出已启动。两端静音切换、Host 停止确认、手机原音频模式和音量恢复全部通过。验收使用真实电脑屏幕与音频，经同一 WebRTC 会话传输。

## 重跑入口

Host 工作区使用全局 Cargo，运行 FFmpeg 测试时将本项目 FFmpeg `bin` 放入 PATH；如 sccache 启动超时，清空 `RUSTC_WRAPPER` 和 `CARGO_BUILD_RUSTC_WRAPPER`。

```powershell
cargo test -p host-windows opus_tests --offline
cargo test -p host-runtime --lib --test session_safety --test m5_audio --offline
cargo test -p host-runtime --test m5_audio --offline -- --ignored --nocapture --test-threads=1
```

最后一条会播放短测试音并短暂切换电脑静音，仅手工验收时运行；测试用恢复守卫保证失败退出也执行停止。

Android 使用 `gradlew.bat :app:assembleDebug :app:assembleDebugAndroidTest :app:testDebugUnitTest --offline --console=plain`。

真机入口是 `runtime/examples/m5_android_fixture.rs` 和 `M5AudioInstrumentedTest.kt`。Fixture 每次启动传入全新的独立临时目录，使用 46671 端口，不加载已安装应用的设置；180 秒或目录内出现 `stop` 文件后结束并停止会话。通过 ADB reverse 转发控制端口，测试参数 `m5HostId / m5PairCode` 从该目录的 `android_fixture.json` 读取，不写入项目配置。同一进程内再次测试时，结束会话会刷新临时验证码，需要从临时目录的 `host_settings.json` 读取新验证码。Windows 屏幕采集需要正常桌面权限，受限运行环境的 BitBlt 失败不能作为音频故障结论。

未提供 Fixture 参数时，真机用例跳过，不能计作真机成功。用例检查收到 Opus 数据、Android 播放启动、两端静音控制、Host 停止确认、手机音频模式和音量恢复；人工听感与长时间影音同步仍需单独确认。
