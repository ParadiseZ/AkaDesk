# AkaDesk 数据结构设计

## 1. 文档目的

本文档只定义 AkaDesk 当前阶段需要统一的数据结构边界，不展开 API 细节、线程模型和具体实现。

目标只有三个：

- 先把跨端共享的数据模型定住
- 先把 Host Runtime 内部状态模型定住
- 先把本地持久化模型定住

当前范围以 V1 为主：

- Android 主控端
- Windows 被控端
- 桌面端 `Tauri Shell + Host Runtime`
- 控制面、媒体协商、输入事件、状态同步

V2 文件传输相关结构本次只预留位置，不在这里展开。

## 2. 文档位置与代码落位

本文档文件位置：

- `docs/数据结构设计.md`

后续代码里的数据结构落位约定：

| 数据类型 | 放置位置 | 说明 |
| --- | --- | --- |
| 跨语言共享协议结构 | `proto/` | 作为唯一协议源，供 Android / Rust / TypeScript 生成或映射 |
| Host 平台抽象共享模型 | `desktop/host/contracts/` | 放 trait 相关共享模型、错误类型、领域结构 |
| Host Runtime 内部状态结构 | `desktop/host/runtime/` | 放运行时状态、会话上下文、诊断快照 |
| Android 本地持久化结构 | `android/app/src/main/java/.../data/` | 放 DataStore DTO、历史记录、偏好设置 |
| Tauri Shell 本地持久化结构 | `desktop/ui/` 或 `desktop/src-tauri/` | 放本地设置、最近设备、诊断偏好 |

建议未来协议文件拆分如下：

- `proto/common.proto`
- `proto/device.proto`
- `proto/session.proto`
- `proto/media.proto`
- `proto/input.proto`
- `proto/ipc.proto`

## 3. 设计原则

### 3.1 一份概念，只保留一个协议主定义

例如：

- `DeviceIdentity`
- `SessionState`
- `VideoCodec`
- `DisplayInfo`

这些概念在跨端上只能有一份 canonical 定义，优先放在 `proto/`。

### 3.2 线上的协议结构和本地 UI ViewModel 分开

不能让以下概念混在一起：

- 协议消息
- Runtime 内部状态
- Android / Tauri UI 显示模型

例如 `SessionSnapshot` 可以作为协议和运行时共享模型，但 `DeviceCardUiState` 这种 UI 结构不能上升为协议结构。

### 3.3 协议字段做增量演进，不做破坏式重命名

必须遵守：

- 新能力优先加新字段
- 枚举保留未来扩展值
- V1 未使用的字段可以先保留，不强行删掉扩展位

### 3.4 V1 先把结构定清，不把实现一次铺满

例如视频：

- V1 只先做 `H.264`
- 但结构上提前预留 `HEVC(H.265)`、`VP8`、`VP9`、`AV1`

例如音频：

- V1 只先做 `Opus`
- 结构上仍保留 codec 扩展位

## 4. 标识与公共字段规范

建议统一以下 ID：

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| `device_id` | `string` | 设备稳定标识，跨会话稳定 |
| `session_id` | `string` | 单次远控会话标识 |
| `request_id` | `string` | 单次请求标识，用于 IPC 或控制面关联 |
| `stream_id` | `string` | 单路媒体流标识 |
| `display_id` | `string` | 显示器标识 |
| `audio_device_id` | `string` | 音频设备标识 |

建议所有跨端消息公共字段至少考虑：

- `version`
- `timestamp_ms`
- `device_id`
- `session_id`
- `request_id`

约定：

- 协议层 ID 先统一使用 `string`
- Rust/Android/TS 各自内部可以再包成强类型
- 时间戳统一使用 `unix epoch milliseconds`

## 5. 协议结构设计

## 5.1 `proto/common.proto`

用途：

- 放公共枚举、基础消息、错误结构、能力位结构

建议核心枚举：

```proto
enum PlatformKind {
  PLATFORM_KIND_UNSPECIFIED = 0;
  PLATFORM_KIND_ANDROID = 1;
  PLATFORM_KIND_WINDOWS = 2;
  PLATFORM_KIND_LINUX = 3;
  PLATFORM_KIND_MACOS = 4;
}

enum RuntimeState {
  RUNTIME_STATE_UNSPECIFIED = 0;
  RUNTIME_STATE_STOPPED = 1;
  RUNTIME_STATE_STARTING = 2;
  RUNTIME_STATE_READY = 3;
  RUNTIME_STATE_SESSION_PREPARING = 4;
  RUNTIME_STATE_STREAMING = 5;
  RUNTIME_STATE_DEGRADED = 6;
  RUNTIME_STATE_STOPPING = 7;
  RUNTIME_STATE_ERROR = 8;
}

enum SessionState {
  SESSION_STATE_UNSPECIFIED = 0;
  SESSION_STATE_IDLE = 1;
  SESSION_STATE_DISCOVERED = 2;
  SESSION_STATE_CONNECTING = 3;
  SESSION_STATE_NEGOTIATING = 4;
  SESSION_STATE_PREPARING = 5;
  SESSION_STATE_STREAMING = 6;
  SESSION_STATE_DISCONNECTING = 7;
  SESSION_STATE_DISCONNECTED = 8;
  SESSION_STATE_FAILED = 9;
}
```

建议基础结构：

```proto
message VersionInfo {
  uint32 schema_version = 1;
  string app_version = 2;
  string build_channel = 3;
  PlatformKind platform = 4;
}

message ErrorInfo {
  string code = 1;
  string message = 2;
  bool retryable = 3;
  string detail = 4;
}

message CapabilityFlags {
  bool supports_audio = 1;
  bool supports_input = 2;
  bool supports_display_control = 3;
  bool supports_hardware_encode = 4;
  bool supports_hardware_decode = 5;
  bool supports_software_encode = 6;
  bool supports_software_decode = 7;
}
```

说明：

- `RuntimeState` 面向 Host 生命周期
- `SessionState` 面向远控会话状态
- `CapabilityFlags` 只放高层能力开关，不把平台细节全塞进去

## 5.2 `proto/device.proto`

用途：

- 描述设备、发现结果、能力摘要、显示器和音频设备快照

建议核心结构：

```proto
message DeviceIdentity {
  string device_id = 1;
  string display_name = 2;
  PlatformKind platform = 3;
  string hostname = 4;
  string app_version = 5;
}

message DevicePresence {
  DeviceIdentity identity = 1;
  string lan_address = 2;
  uint32 control_port = 3;
  bool paired = 4;
  bool reachable = 5;
  int64 last_seen_ms = 6;
}

message DisplayInfo {
  string display_id = 1;
  string name = 2;
  uint32 width = 3;
  uint32 height = 4;
  uint32 refresh_rate = 5;
  uint32 scale_percent = 6;
  bool primary = 7;
  bool hdr = 8;
}

message AudioDeviceInfo {
  string audio_device_id = 1;
  string name = 2;
  bool input = 3;
  bool output = 4;
  bool default_device = 5;
}

message DeviceSnapshot {
  DeviceIdentity identity = 1;
  CapabilityFlags capability_flags = 2;
  repeated DisplayInfo displays = 3;
  repeated AudioDeviceInfo audio_devices = 4;
}
```

说明：

- `DevicePresence` 用于发现列表
- `DeviceSnapshot` 用于连接前能力摘要或桌面端状态展示
- `DisplayInfo` 不带会话设置结果，只描述当前快照

## 5.3 `proto/media.proto`

用途：

- 描述视频/音频 codec、媒体偏好、协商结果、实际运行参数

建议核心枚举：

```proto
enum VideoCodec {
  VIDEO_CODEC_UNSPECIFIED = 0;
  VIDEO_CODEC_H264 = 1;
  VIDEO_CODEC_HEVC = 2;
  VIDEO_CODEC_VP8 = 3;
  VIDEO_CODEC_VP9 = 4;
  VIDEO_CODEC_AV1 = 5;
}

enum AudioCodec {
  AUDIO_CODEC_UNSPECIFIED = 0;
  AUDIO_CODEC_OPUS = 1;
}

enum CodecImplementation {
  CODEC_IMPLEMENTATION_UNSPECIFIED = 0;
  CODEC_IMPLEMENTATION_HARDWARE = 1;
  CODEC_IMPLEMENTATION_SOFTWARE = 2;
}
```

建议核心结构：

```proto
message VideoPreference {
  VideoCodec codec = 1;
  uint32 width = 2;
  uint32 height = 3;
  uint32 fps = 4;
  uint32 bitrate_kbps = 5;
  bool allow_same_codec_software_fallback = 6;
}

message AudioPreference {
  AudioCodec codec = 1;
  uint32 sample_rate = 2;
  uint32 channels = 3;
  uint32 bitrate_kbps = 4;
}

message VideoSessionSpec {
  VideoCodec codec = 1;
  uint32 width = 2;
  uint32 height = 3;
  uint32 fps = 4;
  uint32 bitrate_kbps = 5;
  CodecImplementation host_encoder = 6;
  CodecImplementation controller_decoder = 7;
}

message AudioSessionSpec {
  AudioCodec codec = 1;
  uint32 sample_rate = 2;
  uint32 channels = 3;
  uint32 bitrate_kbps = 4;
}
```

这里按当前项目最终口径定：

- 主控端下发 `VideoPreference`
- 被控端按该目标编码输出视频流
- 主控端优先使用该编码的硬解
- 如果主控端不支持该编码硬解，则回退到同编码软解
- `width/height` 表示目标显示器分辨率，而不是任意采集后缩放目标
- `bitrate_kbps`、`fps`、分辨率允许在运行中调整
- 运行中的分辨率调整允许按重配或重建链路处理
- 传输过程中不允许修改 `codec`

V1 要求：

- 只落 `VIDEO_CODEC_H264`
- `HEVC`、`VP8`、`VP9`、`AV1` 先保留结构位

## 5.4 `proto/session.proto`

用途：

- 描述远控会话、连接意图、会话快照、断开原因

建议核心枚举：

```proto
enum DisconnectReason {
  DISCONNECT_REASON_UNSPECIFIED = 0;
  DISCONNECT_REASON_CONTROLLER_REQUEST = 1;
  DISCONNECT_REASON_CONTROLLED_REQUEST = 2;
  DISCONNECT_REASON_NETWORK_LOST = 3;
  DISCONNECT_REASON_HEARTBEAT_TIMEOUT = 4;
  DISCONNECT_REASON_RUNTIME_ERROR = 5;
}
```

建议核心结构：

```proto
message SessionIntent {
  string session_id = 1;
  string controller_device_id = 2;
  string controlled_device_id = 3;
  string target_display_id = 4;
  bool enable_audio = 5;
  bool enable_input = 6;
  VideoPreference video = 7;
  AudioPreference audio = 8;
}

message SessionNegotiationResult {
  string session_id = 1;
  SessionState state = 2;
  VideoSessionSpec video = 3;
  AudioSessionSpec audio = 4;
  string target_display_id = 5;
  ErrorInfo error = 6;
}

message SessionSnapshot {
  string session_id = 1;
  SessionState state = 2;
  string controller_device_id = 3;
  string controlled_device_id = 4;
  string target_display_id = 5;
  VideoSessionSpec video = 6;
  AudioSessionSpec audio = 7;
  int64 created_at_ms = 8;
  int64 negotiating_started_at_ms = 9;
  int64 preparing_started_at_ms = 10;
  int64 streaming_started_at_ms = 11;
  int64 disconnecting_started_at_ms = 12;
  int64 updated_at_ms = 13;
  int64 closed_at_ms = 14;
}

message SessionClosedEvent {
  string session_id = 1;
  DisconnectReason reason = 2;
  ErrorInfo error = 3;
  int64 closed_at_ms = 4;
}
```

说明：

- `SessionIntent` 是主控想要什么
- `SessionNegotiationResult` 是双方实际谈成什么
- `SessionSnapshot` 是稳定状态展示模型
- `streaming_started_at_ms` 用于计算真正的被控时长
- `negotiating_started_at_ms -> streaming_started_at_ms` 可用于计算连接建立耗时

## 5.5 `proto/input.proto`

用途：

- 描述主控发往被控的输入事件

建议核心枚举：

```proto
enum PointerButton {
  POINTER_BUTTON_UNSPECIFIED = 0;
  POINTER_BUTTON_LEFT = 1;
  POINTER_BUTTON_RIGHT = 2;
  POINTER_BUTTON_MIDDLE = 3;
}

enum KeyAction {
  KEY_ACTION_UNSPECIFIED = 0;
  KEY_ACTION_DOWN = 1;
  KEY_ACTION_UP = 2;
}
```

建议输入事件统一走 oneof：

```proto
message PointerEvent {
  uint64 seq = 1;
  float normalized_x = 2;
  float normalized_y = 3;
  PointerButton button = 4;
  bool pressed = 5;
  int64 timestamp_ms = 6;
}

message ScrollEvent {
  uint64 seq = 1;
  float delta_x = 2;
  float delta_y = 3;
  int64 timestamp_ms = 4;
}

message KeyEvent {
  uint64 seq = 1;
  uint32 key_code = 2;
  KeyAction action = 3;
  bool alt = 4;
  bool ctrl = 5;
  bool shift = 6;
  bool meta = 7;
  int64 timestamp_ms = 8;
}

message InputEvent {
  string session_id = 1;
  oneof payload {
    PointerEvent pointer = 2;
    ScrollEvent scroll = 3;
    KeyEvent key = 4;
  }
}
```

说明：

- V1 先优先覆盖鼠标、键盘、滚轮
- 触控手势和手柄事件后续再扩展
- 坐标统一先用 `normalized_x/y`，避免分辨率切换后语义漂移

## 5.6 `proto/ipc.proto`

用途：

- 描述 `Tauri Shell <-> Host Runtime` 的本地 IPC 消息

建议思路：

- IPC 不重新发明一套领域结构
- IPC 只包一层 envelope
- 业务 payload 尽量复用 `device/session/media/common` 中的结构

建议核心结构：

```proto
enum IpcMessageKind {
  IPC_MESSAGE_KIND_UNSPECIFIED = 0;
  IPC_MESSAGE_KIND_REQUEST = 1;
  IPC_MESSAGE_KIND_RESPONSE = 2;
  IPC_MESSAGE_KIND_EVENT = 3;
}

message IpcEnvelope {
  string request_id = 1;
  IpcMessageKind kind = 2;
  string type = 3;
  bytes payload = 4;
  int64 timestamp_ms = 5;
}
```

建议第一批 IPC `type`：

- `GetRuntimeStatus`
- `RuntimeStatusChanged`
- `GetCapabilitySnapshot`
- `CapabilitySnapshotChanged`
- `StartSession`
- `StopSession`
- `SessionChanged`
- `DiagnosticEvent`

说明：

- `payload` 内部仍然是 Proto 序列化后的具体消息
- IPC 层不直接承载视频帧和音频帧
- IPC 只承载控制、状态、诊断和命令

## 6. Host Runtime 内部结构设计

这一层不是跨端协议，而是 Rust 内部领域结构。

建议放置位置：

- `desktop/host/contracts/`
- `desktop/host/runtime/`

## 6.1 `contracts` 层建议结构

建议保留这些共享领域结构：

- `DeviceId`
- `SessionId`
- `DisplayId`
- `AudioDeviceId`
- `InputCapabilitySnapshot`
- `CapabilitySnapshot`
- `DisplaySnapshot`
- `AudioDeviceSnapshot`
- `VideoSessionSpec`
- `AudioSessionSpec`
- `PointerInputCommand`
- `ScrollInputCommand`
- `KeyInputCommand`
- `HostError`

这里的原则是：

- 和平台实现、Runtime 编排都要共享的结构，放 `contracts`
- 只属于某个运行时步骤的临时状态，不放 `contracts`

## 6.2 `runtime` 层建议结构

建议最少有以下内部状态：

```text
RuntimeStatus
SessionContext
SessionRegistry
CapabilityCache
DiagnosticBuffer
```

建议职责：

- `RuntimeStatus`
  - 记录 Host 当前生命周期状态
- `SessionContext`
  - 记录单个会话的协商结果、显示器目标、媒体参数、WebRTC 句柄
- `SessionRegistry`
  - 管理当前活动会话和历史会话摘要
- `CapabilityCache`
  - 缓存当前平台能力快照，避免每次都全量重新探测
- `DiagnosticBuffer`
  - 缓存最近的日志事件、错误事件和告警摘要

## 6.3 视频运行时结构

V1 这里要明确只围绕 `H.264` 设计，但结构预留扩展位。

建议保留：

```text
VideoPreference
VideoSessionSpec
VideoPipelineState
EncoderSelection
DecoderSelection
```

建议语义：

- `VideoPreference`
  - 来自主控端，描述目标编码和目标参数
- `VideoSessionSpec`
  - 是双方协商后的最终视频参数
- `VideoPipelineState`
  - 记录当前媒体链路是否已初始化、是否已降级、当前分辨率/帧率/码率
- `EncoderSelection`
  - 记录 Host 端最终使用硬编还是软编
- `DecoderSelection`
  - 记录主控端最终使用硬解还是软解

当前 V1 决策：

- 统一由 `runtime/video` 编排视频主链路
- 先只让这条主链路支持 `H.264`
- 其余编码只在结构上预留，不并行落地

## 6.4 显示器控制结构

建议把“显示器快照”和“显示器设置意图”分开：

```text
DisplaySnapshot
DisplayMode
DisplaySettingIntent
DisplaySettingResult
```

建议语义：

- `DisplaySnapshot`
  - 当前显示器静态与动态信息
- `DisplayMode`
  - 一组可用模式，例如分辨率、刷新率、缩放
  - 至少包含 `width`、`height`、`fps/refresh_rate`、`scale_percent`
- `DisplaySettingIntent`
  - 主控或 Runtime 希望应用到目标显示器的设置
  - 包括会话中分辨率调整时需要应用的目标显示器分辨率
  - 应显式包含 `requested_display_mode`
  - 应显式包含 `history_display_mode`
- `DisplaySettingResult`
  - 实际应用结果，包含成功/失败及回退信息
  - 请求成功时，以 `requested_display_mode` 作为当前生效模式
  - 请求失败时，保持 `history_display_mode` 不变

`history_display_mode` 的作用必须固定：

- 在第一次会话修改显示器设置前记录
- 会话断开时用于恢复原显示器模式
- 至少覆盖：分辨率、缩放倍率、`fps/refresh_rate`

这样后面做：

- 连接前查询
- 会话期间切换
- 会话结束恢复

都会更清晰。

## 7. 本地持久化结构设计

## 7.1 Android 主控端

建议持久化这些结构：

- `ControllerSettings`
- `RecentDeviceRecord`
- `InputProfile`
- `LastSessionPreference`

建议内容：

- `ControllerSettings`
  - 默认码率、默认分辨率、默认 FPS、音频开关、输入偏好
- `RecentDeviceRecord`
  - 最近连接设备、最近连接时间、上次成功会话摘要
- `InputProfile`
  - 鼠标灵敏度、按键映射、手势偏好
- `LastSessionPreference`
  - 上一次成功使用的视频偏好和显示器选择

不建议持久化：

- 运行时瞬时媒体状态
- 高频统计值
- 临时诊断事件

## 7.2 Tauri Shell

建议持久化这些结构：

- `DesktopSettings`
- `WindowState`
- `RecentDiagnosticFilter`
- `KnownControllerRecord`

建议内容：

- `DesktopSettings`
  - 开机自启、托盘行为、日志级别、通知偏好
- `WindowState`
  - 窗口大小、位置、最后打开页签
- `RecentDiagnosticFilter`
  - 最近一次诊断筛选条件
- `KnownControllerRecord`
  - 已知主控设备摘要、最近连接时间

不建议把以下内容长期落本地：

- 完整会话日志明细
- 高频事件原始流
- 视频/音频统计采样点全量历史

## 9. 本次结论

这份数据结构设计文档已经固定放在：

- `docs/数据结构设计.md`

后续实现时按下面的边界落：

- 跨端共享协议结构放 `proto/`
- Host 共享领域结构放 `desktop/host/contracts/`
- Host 运行时内部状态放 `desktop/host/runtime/`
- Android 和 Tauri 的本地持久化结构各自放本端代码目录

先做的重点不是把所有结构都实现，而是先把 `V1 必须先定住的结构清单` 转成 `proto/` 和 Rust 领域模型。
