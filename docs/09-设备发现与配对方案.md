# AkaDesk 设备发现与配对方案

## 1. 文档目的

本文档用于固定 AkaDesk V1 的：

- 局域网设备发现方案
- 发现后控制入口建立方式
- 配对流程
- 配对凭证保存方式
- 未配对设备的信息暴露范围
- 失败与异常处理规则

本文档只描述发现和配对，不展开会话媒体链路和本地 IPC。

## 2. 文档位置

本文档固定放在：

- `docs/09-设备发现与配对方案.md`

## 3. V1 范围

V1 当前只支持：

- Android 主控端
- Windows 被控端
- 局域网内发现
- 局域网内首次配对
- 配对后的本地直连重连

V1 不做：

- 云端账号体系
- 互联网发现
- 云端配对同步
- 跨网络自动打洞

## 4. 参与方

本方案涉及四个参与方：

1. `Android Controller`
2. `Host Runtime`
3. `Tauri Shell`
4. `LAN`

职责：

- `Android Controller`
  - 浏览局域网设备
  - 发起控制连接
  - 发起配对
  - 保存本机侧配对凭证
- `Host Runtime`
  - 对外发布发现信息
  - 接收控制连接
  - 校验配对凭证
  - 生成配对挑战
  - 保存被控端配对记录
- `Tauri Shell`
  - 展示配对验证码和配对状态
  - 提供本地用户可见的配对入口和管理入口
- `LAN`
  - 设备广播和发现所在的本地网络

## 5. 发现方案

## 5.1 V1 结论

V1 设备发现固定采用：

- `mDNS`

不再采用：

- 受控 UDP 广播

原因：

- 局域网设备发现语义更清晰
- 服务发布和浏览更自然
- 后续更容易和固定服务入口绑定

## 5.2 发现层职责

发现阶段只解决两件事：

1. Android 能看到可连接的被控设备
2. Android 能拿到控制连接入口

发现阶段不做：

- 配对确认
- 完整鉴权
- 会话建立
- 媒体协商

## 5.3 服务发布模型

建议每个被控端发布一个固定服务：

- 服务类型：`_akadesk._tcp.local.`

发布主体：

- `Host Runtime`

发布内容：

- 控制连接地址
- 控制连接端口
- 设备最小摘要

## 5.4 mDNS 公布字段

V1 发现阶段只公布最小必要信息。

建议通过 `mDNS` 服务实例名或 `TXT` 记录暴露这些字段：

- `device_id`
- `display_name`
- `platform`
- `hostname`
- `app_version`
- `control_port`
- `reachable`

不建议在发现层直接公布：

- 详细显示器模式列表
- 详细音频设备列表
- 编码器能力细节
- 配对凭证信息

## 5.5 `paired` 字段的 V1 处理

当前数据结构里有：

- `DevicePresence.paired`

但在 `mDNS` 浏览阶段，主控端并不会先把自己的 `controller_device_id` 发给被控端，因此这个字段不能被当成“针对当前主控是否已配对”的绝对真值。

V1 建议约束：

- 发现列表中的 `paired` 不作为最终认证判断依据
- 实际是否已配对，以后续 `ControlHello` 认证结果为准

也就是说：

- 发现层负责“看到设备”
- 控制层负责“确认这台主控能否直接进入会话”

## 6. 控制入口建立

## 6.1 控制连接方式

发现完成后，Android 应直接连接：

- `Host Runtime` 暴露的控制层 `WebSocket`

控制层承载：

- `ControlHello`
- `PairingRequest`
- `PairingChallenge`
- `PairingConfirm`
- `PairingResult`
- 心跳
- 后续会话建立请求

控制层 `WebSocket` 二进制帧统一使用：

- `ControlEnvelope`

它负责固定 `request_id`、消息 `kind`、业务 `type` 和 Protobuf `payload`。

## 6.2 建立顺序

建议顺序：

1. Android 通过 `mDNS` 获得设备入口
2. 用户选择目标设备
3. Android 建立控制层 `WebSocket`
4. Android 发送 `ControlHello`
5. Host Runtime 返回认证结果
6. 已配对则直接继续
7. 未配对则进入配对流程

## 7. 配对方案

## 7.1 V1 结论

V1 首次配对固定采用：

- 一次性验证码挑战

不采用：

- 自动免确认配对
- 云端扫码

## 7.2 为什么选验证码挑战

因为它满足 V1 当前约束：

- 简单
- 本地可见
- 容易审计
- 不依赖额外基础设施

## 7.3 V1 配对流程

V1 推荐流程：

1. Android 发现未完成可信认证的被控设备
2. Android 发起 `PairingRequest`
3. Host Runtime 生成一次性验证码和 `challenge_id`
4. Tauri Shell 显示该验证码
5. Android 收到 `PairingChallenge`
6. 用户在 Android 输入验证码
7. Android 发送 `PairingConfirm`
8. Host Runtime 校验成功后生成 `pair_token`
9. 双端分别持久化配对结果

## 7.4 配对挑战内容

建议挑战至少包含：

- `request_id`
- `challenge_id`
- `challenge_type`
- `verification_code`

说明：

- `verification_code` 由 Host Runtime 生成
- 实际展示由 `Tauri Shell` 负责
- `M3` 当前实现会把 `verification_code` 随 `PairingChallenge` 一并返回，便于 Android 首轮联调和回归测试；后续是否继续对主控端暴露该字段，可再按安全口径收紧

## 7.5 验证码建议

V1 建议：

- 8位数字或英文字符
- 临时验证码模式：断开连接后重新生成
- 自定义验证码模式：长期有效

自定义验证码的失效条件固定为：

- 用户手动从自定义验证码模式切换回临时验证码模式

补充约束：

- 主控端取消配对只删除主控端本地保存的配对凭证
- 不影响被控端当前验证码模式
- 自定义验证码不因 Host 重启而失效

## 7.6 配对成功后的结果

配对成功后 Host Runtime 应生成：

- `pair_token`

并将它绑定到：

- `controller_device_id`
- `controlled_device_id`

## 8. 配对凭证持久化

## 8.1 被控端保存内容

被控端建议维护：

- `paired_controllers`

每条记录建议至少保存：

- `controller_device_id`
- `controller_display_name`
- `pair_token_hash`
- `created_at_ms`
- `last_used_at_ms`
- `revoked_at_ms` 或等价状态位

注意：

- 被控端不建议明文保存 `pair_token`
- 建议保存摘要或受保护形式

## 8.2 主控端保存内容

建议至少保存：

- `device_id`
- `controller_device_id`
- `pair_token`
- `paired_at_ms`
- `last_used_at_ms`

说明：

- 需要保存可用于后续直连认证的凭证
- 如果用户主动取消配对，应删除本地保存的该设备凭证

## 8.3 凭证使用方式

后续重连时：

1. Android 先发 `ControlHello`
2. 同时携带：
   - `controller_device_id`
   - `pair_token`
3. Host Runtime 验证通过后允许继续会话协商

## 9. 未配对设备的暴露范围

V1 要求未配对设备：

- 可以被发现
- 但只能暴露最小必要信息

允许暴露：

- `device_id`
- `display_name`
- `platform`
- `hostname`
- `app_version`
- 控制连接入口

不允许在未认证前暴露：

- 详细显示器模式
- 详细音频设备信息
- 详细编码器能力
- 最近配对记录
- 会话历史

详细能力应在：

- `ControlHello` 认证成功后

再返回。

## 10. 失败处理

## 10.1 发现失败

常见失败：

- `mDNS` 浏览超时
- 网络接口不可用
- 目标设备未发布服务

建议处理：

- UI 提示未发现设备
- 允许重新扫描
- 不缓存“不可达”太久

## 10.2 控制连接失败

常见失败：

- `WebSocket` 无法建立
- 控制端口不可达
- TLS/协议握手失败

建议处理：

- 返回连接失败提示
- 保持在发现列表
- 允许再次发起连接

## 10.3 配对失败

常见失败：

- 验证码错误
- 用户在被控端取消配对

建议处理：

- 当前挑战失效
- Host Runtime 清理该挑战
- Android 需重新发起 `PairingRequest`

## 10.4 认证失败

常见失败：

- `pair_token` 无效
- `pair_token` 已撤销
- `controller_device_id` 不匹配

建议处理：

- 返回认证失败
- 不进入会话协商
- 允许用户重新走配对流程

## 11. 撤销与重新配对

V1 至少要支持：

- 被控端删除某个已配对主控
- 主控端删除某个已配对被控设备

撤销后规则：

- 旧 `pair_token` 立即失效
- 下次连接必须重新配对

## 12. 推荐状态流

发现与配对相关状态建议理解为：

1. `DISCOVERING`
2. `NEGOTIATING`
3. `PREPARING`

其中：

- 发现设备属于 `DISCOVERING`
- `ControlHello` 鉴权、配对请求、验证码验证都属于 `NEGOTIATING`
- 配对完成后的媒体准备才进入 `PREPARING`

## 13. V1 最小闭环

如果只按最小闭环落地，发现与配对第一版必须先做：

1. `mDNS` 设备发布
2. `mDNS` 设备浏览
3. 控制层 `WebSocket` 入口
4. `ControlHello`
5. `PairingRequest`
6. `PairingChallenge`
7. `PairingConfirm`
8. `PairingResult`
9. `pair_token` 持久化
10. 配对后重连认证

## 14. 本次结论

设备发现与配对方案文档固定放在：

- `docs/09-设备发现与配对方案.md`

V1 当前正式口径是：

- 发现固定用 `mDNS`
- 控制连接固定走 `WebSocket`
- 首次配对固定走一次性验证码挑战
- 认证凭证固定为 `pair_token`
- 未配对设备只暴露最小必要信息

后续如果继续，最自然的动作就是把这份文档里的发现、配对、认证消息收敛回 `proto/` 和控制层状态机。
