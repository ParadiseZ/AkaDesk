# AkaDesk 开发里程碑切片

## 1. 文档目的

本文档用于把 AkaDesk 的开发推进方式固定成“可追踪交付物切片”。

它解决的是：

- 每个阶段到底做什么
- 每个阶段到底会落哪些文件和模块
- 后期如何快速知道已经写了什么
- 哪些内容明确还没做
- 每个阶段怎么验收

本文档不替代技术选型或架构设计，而是把这些结论转成可执行的工程切片。

## 2. 文档位置

本文档固定放在：

- `docs/11-开发里程碑切片.md`

## 3. 切片原则

每个里程碑必须同时写清 6 件事：

1. 目标
2. 交付物
3. 涉及文件或目录
4. 验收标准
5. 明确不包含内容
6. 风险与后补

这样后期要回看“到底写了什么”，不靠记忆，只看：

- 交付物清单
- 涉及目录
- 验收结果

## 4. 记录规则

每完成一个里程碑，后续必须补三类记录：

### 4.1 范围账

本次计划做什么：

- 本里程碑目标
- 本里程碑边界

### 4.2 实现账

本次实际落了什么：

- 新增了哪些目录
- 新增了哪些文件
- 修改了哪些关键模块
- 新增了哪些协议、trait、状态、错误码

### 4.3 验证账

本次如何证明有效：

- 跑了哪些命令
- 做了哪些手动验证
- 没验证哪些风险

## 5. 里程碑总览

建议当前项目按下面的顺序推进：

| 里程碑 | 名称 | 最小成果 |
| --- | --- | --- |
| `M0` | 文档基线 | 技术与边界文档定稿 |
| `M1` | 协议与骨架 | `proto/` 与 `desktop/host/*` 骨架建立 |
| `M2` | 桌面壳与本地 IPC | `desktop-shell` 拉起 `host-runtime` 并建立 IPC |
| `M3` | 发现与配对 | `mDNS + WebSocket + pairing` 跑通 |
| `M4` | 视频主链路 | `H.264` 单路视频预览跑通 |
| `M5` | 音频链路 | `Opus` 音频采集与传输跑通 |
| `M6` | 输入控制 | 鼠标、滚轮、键盘注入跑通 |
| `M7` | 显示器控制与恢复 | 分辨率/缩放/FPS 修改与 `history_display_mode` 恢复跑通 |
| `M8` | 诊断与稳定性 | 日志、错误、诊断导出、降级与重连补齐 |
| `M9` | V2 文件传输 | 基础文件传输闭环 |

## 6. `M0` 文档基线

### 6.1 目标

把项目重启后的核心边界先定住。

### 6.2 交付物

- `01-技术选型.md`
- `02-数据结构设计.md`
- `03-项目流程图.md`
- `04-协议设计.md`
- `05-模块与目录设计.md`
- `06-状态机定义.md`
- `07-contracts接口设计.md`
- `08-视频主链路设计.md`
- `09-设备发现与配对方案.md`
- `10-错误码与诊断模型.md`
- `11-开发里程碑切片.md`
- `12-音频链路设计.md`

### 6.3 涉及目录

- `docs/`

### 6.4 验收标准

- 核心边界不再互相冲突
- 文档之间的命名、路径、职责口径一致
- 开发人员可以只看文档就知道 V1 主线

### 6.5 明确不包含

- 任何运行时代码
- `proto/` 正式文件
- Tauri 或 Rust 工程骨架

### 6.6 风险与后补

- 文档定稿不代表代码无返工
- 真正起骨架后仍可能暴露模型细节问题

### 6.7 范围账

- 本轮 `M0` 只处理 `docs/` 内文档基线，不进入任何运行时代码目录
- 目标是把文件名、交叉引用、目录示例和阶段口径统一到仓库真实现状

### 6.8 实现账

- 将 `M0` 交付物中的 `12-音频主链路设计.md` 修正为真实文件 `12-音频链路设计.md`
- 统一 `01-技术选型.md` 与 `05-模块与目录设计.md` 中 `docs/` 目录示例的文件名口径
- 移除 `03-项目流程图.md` 中带本机绝对路径的文档链接
- 修正 `01-技术选型.md` 中实施顺序建议的阶段编号与条目归属

### 6.9 验证账

- 通过 `Get-ChildItem docs` 核对 `docs/` 实际文件清单
- 通过 `rg` 检查旧文件名、绝对路径链接和错误阶段编号是否已清理
- 手动复核 `M0` 文档与仓库真实文件名、路径、职责描述是否一致

  - `pairing.proto`
  - `session.proto`
  - `media.proto`
  - `input.proto`
  - `ipc.proto`
- `desktop/host/contracts/`
- `desktop/host/ipc/`
- `desktop/host/runtime/`
- `desktop/host/windows/`
- `desktop/host/linux/`
- `desktop/src-tauri/`
- `desktop/ui/`

### 7.3 涉及目录

- `proto/`
- `desktop/host/`
- `desktop/src-tauri/`
- `desktop/ui/`

### 7.4 验收标准

- 所有目录存在
- Rust workspace 和 crate 命名与 `05-模块与目录设计.md` 一致
- 基础 `proto` 文件可通过生成链检查

### 7.6 风险与后补

## 8. `M2` 桌面壳与本地 IPC

### 8.1 目标

让 `desktop-shell` 可以拉起 `host-runtime`，并建立稳定本地 IPC。

### 8.2 交付物

- `desktop-shell` 进程启动骨架
- `host-runtime` 进程入口
- `interprocess + protobuf` IPC client/server
- `GetRuntimeStatus`
- `RuntimeStatusChanged`
- `GetCapabilitySnapshot`

### 8.3 涉及目录

- `desktop/src-tauri/`
- `desktop/host/ipc/`
- `desktop/host/runtime/`

### 8.4 验收标准

- 桌面壳能拉起 Host
- Host 能建立 IPC server
- 桌面壳能拿到 `RuntimeStatus` 和 `CapabilitySnapshot`

### 8.5 明确不包含

- 远程发现
- 配对
- 会话建立
- 视频音频输入链路

### 8.6 风险与后补

- Windows 子进程管理、退出清理和日志桥接可能后补

## 10. `M4` 视频主链路

### 10.1 目标

跑通 `H.264` 单路视频预览。

### 10.2 交付物

- `runtime/video`
- `CaptureQueryPort`
- `CaptureControlPort`
- `VideoEncoderQueryPort`
- `VideoEncodePort`
- Windows 采集：
  - 优先 `WGC`
  - 回退 `DXGI`
- Host 端 `H.264` 硬编优先
- Host 端 `H.264` 软编回退
- 主控端 `H.264` 硬解优先
- 主控端 `H.264` 软解回退

### 10.3 涉及目录

- `desktop/host/runtime/src/video/`
- `desktop/host/contracts/src/cap/`
- `desktop/host/contracts/src/encode/`
- `desktop/host/windows/src/cap/`
- `desktop/host/windows/src/encode/`
- `android/`

### 10.4 验收标准

- 单路视频预览稳定显示
- `VideoSessionSpec` 可观测
- 硬编失败可回退软编
- 主控硬解失败可回退同编码软解

### 10.5 明确不包含

- 极复杂自适应码控

### 10.6 风险与后补

- 第三方 crate 能力不足时，后续可能需更换实现路径
- `HEVC/VP8/VP9/AV1`

## 11. `M5` 音频链路

### 11.1 目标

跑通系统音频采集、`Opus` 传输，以及断开后的音频输出设置恢复。

### 11.2 交付物

- `runtime/audio`
- `AudioDeviceQueryPort`
- `AudioCapturePort`
- `history_audio_output_setting`
- `mute_controlled_local_playback`
- `mute_controller_local_playback`
- Windows 音频采集实现
- `Opus` 编码接入

### 11.3 涉及目录

- `desktop/host/runtime/src/audio/`
- `desktop/host/contracts/src/audio/`
- `desktop/host/windows/src/audio/`
- `android/`

### 11.4 验收标准

- 主控端可听到被控系统音频
- 采集策略按“同一输出设备 loopback capture + 本地静音”跑通
- 主控端可动态切换被控端静音
- 主控端可动态切换主控端本地静音，且不触发 Host 端重协商
- 断开后正确恢复 `history_audio_output_setting`

### 11.5 明确不包含

- 多路混音
- 独立虚拟输出设备策略
- 单独的音频传输开关

### 11.6 风险与后补

- 不同 Windows 音频设备上的 endpoint mute / loopback 行为可能不一致

### 14.2 交付物

- `DiagnosticSnapshot`

- 错误码与用户提示映射
- `DEGRADED` 状态可视化

### 14.3 涉及目录

- `desktop/src-tauri/`
- `desktop/ui/`

### 14.6 风险与后补

## 16. 如何保证后期知道“写了哪些内容”

后期不靠记忆，靠这份文档里的三类信息：

1. `交付物`
   - 看本里程碑本来应该落什么
2. `涉及目录`
   - 看本里程碑通常会改哪里
3. `验收标准`
   - 看哪些行为已经被证明可用

如果后续真正执行里程碑，建议在每个里程碑完成后再追加：

- 已完成项
- 未完成项
- 验证记录

这样这份文档就不仅是计划表，也是实施账本。

## 17. 本次结论

开发里程碑切片文档固定放在：

- `docs/11-开发里程碑切片.md`

它不是泛泛的“阶段目标”，而是：

- 每个阶段交付什么
- 改哪些目录
- 怎么验收
- 明确不做什么

后续如果继续，最自然的动作就是按 `M1` 开始真正起工程骨架。
